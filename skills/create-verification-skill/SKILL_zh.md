# 创建验证 skill

在 Claude Code 中，每个会话开始遵循此 skill 之前，请阅读一次 [the Claude Code adapter](../../docs/harness/claude-code.md)。它将 pstack skills 中的 Cursor 名称映射到 Claude Code。

每个正式项目都需要一种可编写脚本的方式来驱动真实应用并证明其行为：启动它，以用户的方式操作某项功能，并捕获证据。此 skill 会生成一个针对该 repo 定制的项目本地 skill（`.cursor/skills/verify-<app>/`）。你要为下一个智能体编写生成器的输出，而不是为人类编写：它将在任务执行中途被一个从未见过该应用的智能体冷读。

## 1. 访谈 repo，而不是用户

以下问题从代码库中回答，只询问你无法观察到的内容：

- **Surface（交互界面）：** 用户实际接触的是什么？Web UI、CLI/TUI、桌面应用、API、移动应用，还是库？一个 repo 可能有多个界面；选定主要界面，并记录其余界面。
- **Run（运行）：** 应用如何在本地启动？优先使用 repo 自己记录的开发命令（package scripts、Makefile、README 快速入门）。记录端口、环境变量、种子数据和认证方式。
- **Drive（驱动）：** 智能体如何以编程方式与其交互？优先使用现有的测试工具——Playwright/Cypress 规范、expect 脚本、PTY 辅助工具、可通过 curl 访问的端点、调试端口。只有在这些都不适用时，才选择通用方案：Web 和 Electron 使用 browser/CDP，CLI/TUI 使用 tmux/PTY 工具，服务使用纯 HTTP。
- **Observe（观察）：** 可以捕获哪些证据？截图、终端记录、响应体、日志、退出码、数据库状态。
- **Isolate（隔离）：** 两个实例能否并行运行（端口、数据目录、配置文件）？如果不能，就在生成的 skill 中说明：拒绝对共享实例进行双重驱动，远比破坏用户的会话要好。

如果 checkout 无法按原样构建或启动，先修复它（或准确报告问题），再进行生成；基于一个损坏的基础编写的 skill 会教授错误的步骤。当一个无关的缺失资源阻止启动（API 从不提供服务的静态目录、示例配置）时，生成的 skill 可以创建它，并明确标记为验证脚手架，并在清理时删除。

## 2. 生成 skill

编写 `.cursor/skills/verify-<app>/SKILL.md`，包含 YAML frontmatter（`name: verify-<app>`，以及一个 `description`，说明应用名称、界面以及何时使用它——没有 frontmatter，skill 就永远不会被注册），并包含以下章节，每个章节都基于访谈实际发现的内容（不留占位符）：

- **Launch（启动）：** 启动应用以进行验证的确切命令，以及如何判断它已就绪（一行日志或一个提示符）。启动必须能从空数据目录进入可用状态，包括任何迁移和种子数据。"就绪"意味着可用，而不仅仅是进程响应。数据库健康检查可能通过，而其初始化脚本仍在运行。包括拆除步骤。对于短暂运行的 CLI 或 TUI，不存在需要保持运行的服务器：启动意味着一次性构建二进制文件（或安装依赖），然后在各自隔离的 PTY 或 tmux 会话中启动每次驱动。
- **Doctor（诊断）：** 一个只读检查，用于回答"这个实例值得驱动吗？"——进程是否在运行、版本/构建是否正确、端口是否归我们所有、认证是否有效。当任何情况看起来不对时，智能体首先运行它。
- **Drive（驱动）：** 使用本 repo 中真实选择器/命令的 harness 操作流程，而不是示例。优先使用稳定的句柄（ARIA 标签、data 属性、提示符字符串、路由路径），而不是坐标和 Tab 顺序。
- **Evidence（证据）：** 为证明而捕获的内容以及存放位置。说明证明标准：演练真实的用户路径，而非内部 setter 或仅用于测试的端点；同时捕获操作及其产生的状态，而不仅仅是最终屏幕；在可见内容之外，还要验证副作用（写入的文件、插入的行、发送的消息）；只有在生产边界已将外部系统隔离的地方才使用 mock。当安全路径是 dry-run 或测试模式时，应通过观察（文件、网络、git 引用）来验证它实际跳过了什么，而不是相信其名称：某些 dry-run 仍会访问网络或打开浏览器。
- **Cleanup（清理）：** 如何拆除本次运行创建的实例。绝不按进程名称杀死进程；只杀死你自己启动的进程。清理会删除实例和临时状态，但绝不删除证据：证明性产物在拆除后仍保留，并存放于 skill 中指明的位置。
- **Helpers（辅助工具）：** 该 skill 附带的任何脚本都必须可执行，并且其调用方式要在 skill 正文中展示。读者需要自行逆向推断的辅助工具，不算辅助工具。

## 3. 填充功能地图

创建 `.cursor/skills/verify-<app>/features/README.md`，以及每个你能识别出的面向用户功能的一个文件（起步时争取覆盖最重要的 3-5 个，从路由、命令、菜单或文档中选取）。遵循 [`references/feature-map-example/`](references/feature-map-example/) 的结构，包含一个 README 索引和每个功能一个文件。每个文件都从用户视角回答：功能是什么、如何到达它、如何用 harness 驱动它，以及什么样的可观察最终状态证明它可用。四个 H2 分别是 `Sub-features`、`How to get to it (user POV)`、`Driving it with <harness>` 和 `Gotchas`。如果种子数据缺少某个旅程所需的前置条件，该旅程应报告失败，并将原因记入该功能的 `Gotchas`。绝不为了让旅程通过而削弱它。该地图是 repo 持续维护的验证来源；当地图列出了其他入口时，只驱动一个便捷入口的证明是不完整的。

## 4. 在交付前证明生成的 skill

端到端地运行其自身的说明一次：启动、诊断、驱动**一个**已映射的功能（一个就够了；地图存在的意义是让之后的运行可以覆盖其余功能）、捕获证据、清理。清理之后，确认证据仍存在于指定位置——如果清理吞掉了证明，则此步骤失败。修复失败项，并且在每次失败的迭代之后也运行生成的清理步骤，以免失败的尝试遗留进程和端口。从未执行过的生成 skill 只是草稿，不是交付物。如果你是在替代目标（用容器代替全新 VM，用本地栈代替远程栈）中证明的，请列出替代目标所做而真实目标不会做的每一个设置步骤。这些步骤在真实目标上完成运行之前，保持未验证状态。

## 5. 提供维护循环

请用户使用 `/maintain-verification-skill` 来保证地图随应用变化而保持准确。仅在用户询问时才建议维护节奏。
