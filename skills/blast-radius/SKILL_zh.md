# 影响范围

在变更上线前，找出它会破坏哪些其他部分。适用于 "blast radius of X"、"what could this break"，或审查你还不放心的小 diff。

与 `how` 和 `why` 配合使用。`how` 告诉你代码做了什么。`why` 告诉你代码为什么是这样的结构。影响范围告诉你它会在别处破坏什么。

只列出调用方不是这项工作的目的。agent 用 grep 几秒钟就能找到这些。这项工作的目的是找出 grep 发现不了的破坏。

## 不要相信你自己的书面分析

听起来正确的影响范围分析毫无价值。无论它是否属实，读起来都很有说服力。所以不要只交出书面分析。找出整个分析所依赖的一两个事实，并通过运行代码来证明它们。

### 你有多确定

对于变更安全性所依赖的每一个事实，尽量沿着下面的列表往下走（在成本可控的前提下），并说明你停在了哪一级。

1. 你说了它。单凭这一点毫无价值。
2. 你指出了那一行。给出真实的 `file:line`，或库自身的源码。
3. 你证明了坏情况不会发生。你逐步推演了故障过程，它不会到达。
4. 你运行了它。用一个脚本或测试调用真实代码，如果你判断错误则大声失败。
5. 你在运行中的应用里复现了它。

第 4 级通常是一个小脚本：导入应用所发布的同一个库，并调用你担心的那个确切函数。

## 步骤

1. 阅读变更。包括 diff、新增、修改和删除的符号，以及它现在有哪些不同的行为，包括 diff 没有明确说明的部分。使用 `why` 的第 2 步来拉取 PR 和 commit。
2. 找出它安全所依赖的那一个事实。大多数看起来有风险的变更，其实只依赖于一个事实，例如"这个调用只会丢弃已经失效的缓存条目，除此之外什么都不做"。找到这个事实。如果它成立，大多数风险情形会一并被排除。把时间花在这里，而不是花在一长串"也许"上。
3. 查看 grep 看不到的地方。阅读你调用的库的源码，检查其固定版本以及任何本地补丁。弄清代码在什么时候运行：微任务、卸载和清理、Solid 与 React 的差异。追踪符号搜索遗漏的东西：API 返回的 JSON、数据库列、传输格式、读取同一字节的其他语言、功能开关、下游三跳之外的代码。
4. 对每个风险保持诚实。判断它发生的真实可能性以及发生时的真实代价。保留你已确认的风险。把你检查过并排除的风险单独列出。遵循与 `why` 相同的规则。引用真实的 `file:line`，找不到任何结果的搜索也是一种答案，绝不编造调用方或 API。
5. 证明那一个事实。编写一个运行真实代码的脚本或测试，运行它，并粘贴实际发生的结果。
6. 对于大型或范围广的变更，将其作为 `arena` 运行。向多个模型提出同一个问题并合并答案。不同的模型会发现不同的真实 bug。

## 交付内容

- **它做了什么。** 改变了什么，包括不明显的部分。
- **它安全所依赖的那一个事实。** 说明该事实，说明你把它推进到了哪一步，并展示证明。如果你无法证明，就写 unproven。
- **风险。** 每条都要说明它如何被破坏、`file:line`、发生的可能性和严重程度，以及如何检查。对于重要的风险，粘贴证明。
- **已排除。** 你检查过什么，以及为什么它没问题。
- **合并前。** 能捕获真实 bug 的最便宜的测试或复现步骤，包括你编写的脚本。

通过 `unslop` 撰写，引用真实代码，并在发布到任何公开场合之前删除所有私密内容。

**回复：** 上述书面内容，其中那一个安全事实要么已被证明，要么标记为 unproven。
