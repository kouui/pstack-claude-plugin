### 自主运行

**你对退出条件负责。先定义完成标准，然后不停顿地朝它推进。**

1. 在第一次迭代之前，把退出条件写成可检查的谓词（测试全部通过、复现问题已修复、N 个 PR 全部合并、像素差异为零）。
2. 使用 Cursor 的 `/loop` 命令（内置命令，不是 pstack skill）选择唤醒机制。需要监听的事件（CI、合并、ref 前进）配一个观察者子代理，由它在事件发生时唤醒你，并以较长的基于时间的心跳作为兜底。没有事件的情况，则使用固定间隔的心跳，间隔长短取决于结果值得重新检查的时机。按照 Subagents 一节，为每个子代理选择推理级别以及 fast 或 standard 速度，使其匹配任务。
3. 每次迭代都只做证据所支持的最小改动，用谓词验证，若有进展则提交，若没有帮助则丢弃改动。"也许有帮助"的冗余改动应当被回退，而不是留着随波逐流。
   依据 **sequence-verifiable-units** principle skill 安排工作顺序，每个单元在进入下一单元之前先验证，而不是把所有检查堆到最后。
4. 运行过程中的新发现由你自己处理。损坏的 skill、相关 bug、不稳定的验证器、review 噪声、工具故障、被遗弃的后续工作以及可修复的漂移，都通过 poteto-mode 自行解决。带外修复放进它们自己的 PR。不要把可逆的工作留给人类，也不要使用 `AskQuestion`。只上报不可逆的操作、任何实验都无法判定的真正产品或偏好决策，或者真正的死路。谓词始终是主线，每次处理完旁支修复后都要回到谓词上。
5. 每次迭代都通过 **show-me-your-work** skill 做一次检查点，记录一行：改动了什么，以及谓词是否有所推进。
6. 谓词满足时停止。停滞不是停止的理由，继续推进，并调整方法以突破停滞。遇到真正的死路时应当上报，而不是空转。绝不能为了宣布胜利而放宽谓词。

**回复:** 退出条件、迭代次数、已落地的内容、已丢弃的内容、最终谓词状态。
