### Bug fix

**你对这项任务负责。规划、评审、验证。** 将调查和修复委派给子代理，你留在主控位置。按照 Subagents 一节的规定，为每个子代理选择推理级别以及快速或标准速度，以适应该工作。

保持科学态度。每一行上线的代码都要能追溯到运行时证据。"可能有帮助"的保险式补丁只是假设，不是修复，不得上线。当证据推翻某个假设时，回滚由该假设促成的改动。只上线证据所支持的最小改动，不多做任何事。

1. 通过控制 skill（Non-negotiables）在对应的界面上亲自复现问题，即使调试或插桩协议要求你请用户复现。只有在给出明确、具体的理由，说明控制界面无法触达目标时才询问用户，并且必须先尽可能地用它推进。如果无法直接复现，就合成触发条件、收紧条件，或插入检测代码直到它触发。
2. 对原因进行二分查找。列出候选假设，然后逐一排除，直到剩下一个成立。用受影响子系统上的 `how`，以及用于回归历史的 **why** skill 来生成初始假设。每一轮，选择能切掉剩余问题空间最大部分的分割方式，获取运行时证据，然后排除。当程序状态不清楚时，添加插桩或日志，并在代码运行时读取它们。不要猜测。对于漫长或顽固的排查，使用 Cursor 的 `/loop` 命令驱动。在第 3 步的 architect/interrogate 扇出之前，用运行时证据确认存活下来的*机制*。
3. 规划修复。如果它跨越函数边界，先使用 `architect`。将实现委派给一个子代理，使用你配置的 bug 修复模型（默认 `sonnet high`），并给出明确的范围。
4. 在同一界面上验证。原始复现现在必须通过。"不确定"或界面不对都不算通过，需要标记出来。单元测试只能显示分支行为，不能证明 bug 已不存在。
5. 分阶段提交，使失败的复现在 git 历史中先于修复出现。当 bug 有廉价的本地测试路径时，参见 **tdd** skill 的先写失败测试的节奏。如果测试代价高、依赖大量集成或不清楚，则跳过。
   这是规范的 **sequence-verifiable-units** 原则 skill：先写失败测试，修复位于其上。
6. 运行 **Opening a PR**。

**回复：** 什么坏了、根本原因、修复方案、如何验证。原样粘贴失败后又通过的复现输出。
