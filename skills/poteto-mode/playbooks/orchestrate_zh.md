### 编排

**你负责项目的统筹，绝不负责代码。编写任务简报、清空队列、保持前沿为绿、做决定。** 当整个项目交给一个常驻协调者对话时：跨多日、多个堆叠 PR、数十到数百个子代理，人类每天只检查两次，而不是每五分钟检查一次。驱动单个任务达到判定条件即为 Autonomous run。一次需要定制工作流的雄心勃勃的运行属于 figure-it-out。当工作的时长超过任何单个代理的寿命时，转到此处。单个代理能在会话预算内完成的工作不算一个项目。

流程的繁琐程度必须与项目规模相匹配。对于便宜且几乎相同的单元，按各节指示将流程精简。

其余内容依赖三条规则。

- 完成通知是队列事件，而非中断。
- 每次派生和每次恢复都要原样附上常设指令。
- 任务简报就是成果本身。含糊的简报会悄无声息地失败，因为工作者无法向你提问。

#### 角色与部署位置

- **协调者（本对话）。** 本地运行。负责划定框架、编写任务简报、清空收件箱、负责向人类汇报、做出判断。它从不编写或修改代码。存在冲突的合并、链式 rebase 和代码改动始终作为任务分派。在本地 git 操作成本低的仓库上，协调者可以自己机械地落地已验证的单元（快进或干净的 cherry-pick 工作者的提交，然后 push），这属于记账工作。把已完成的工作排在空闲的 stacker 之后，等于让截止日期一无所获。循环从头到尾都是代理式的。代理只能通过 Task 工具派生、恢复和清空。根据子代理一节，为每个子代理选择其推理级别以及快速或标准速度。状态的读写在清空节点通过 `scripts/orch/orch.ts` 进行，每次一条命令输入、一行输出。CLI 从不派生、等待或唤醒任何东西。
- **子协调者。** 始终本地运行、持久化，每个轨道一个，且仅当项目规模超过单个协调者的清空能力时才设置。协调者自己能够清空的轨道不需要中间层。每增加一层都要重新支付一次完整的上下文说明成本，而阻塞式的子协调者会在父级空闲时隐藏其子代理。负责本轨道的单元和看板，编写其工作者的任务简报，派生自己的工作者和验证者（嵌套可达深度 3，嵌套派生拥有完整的 Task schema）。在波次边界汇总聚合结果。绝不转发子代理的原始报告。将进行中的子代理数量限制在一次清空能处理的范围内，大约十个，采用滚动窗口。绝不采用阻塞式批次，那样每批都要等最慢的子代理。
- **工作者 / 验证者。** 作为子代理运行，每个子代理在各自的本地 git worktree 中工作。优先使用数量更少、职责更广的工作者。每个 worktree 或分支只允许一个写入者（principle-separate-before-serializing-shared-state）。单元的验证者须与其工作者使用不同的模型系列。

层级保持为协调者、轨道、工作者三层。按项目编写轨道分解（构建、落地和验证是常见的切分方式，而非必需的结构）。曾尝试硬编码的 swarm 树，但因过于僵化而被搁置。

#### 存储布局

在当前代理的存储中（路径见系统提示）创建 `orchestrate/<project-slug>/`。每个文件只有一个写入者。所有者发布事实，读取者在读取时聚合。记账使用 `bun scripts/orch/orch.ts`，下文简写为 `orch`；其标准的纯文本 TSV 和 JSON 无需 CLI 也可读取。

- `preferences.md` 是常设指令登记册：带编号的行，每行一条约束（模型策略、堆叠形态与数量、验证标准、禁止路径、升级策略）。将其原样粘贴到每次派生和每次恢复中。指令会在恢复过程中衰减，每丢失一条都会多耗费一次人工轮次。当你发现自己在重复一条指令时，先追加该行再行动（principle-encode-lessons-in-structure）。
- `overview.md` 是持久的 PR 与 issue 数据库。只追加，绝不针对每个事件整体重写。
- `units.tsv` 每个单元一行：id、track、state、branch、PR、head SHA、brief path。原地更新行。
- `frontier.json` 是计算得出的合并前沿，依据堆叠安全一节。
- `ledger.tsv` 是验证台账，依据验证一节。
- `inbox/` 存放完成指针。`gates.md` 记录人工关卡（问题、选项、无回复时的默认值）。
- `decisions.tsv` 是通过 show-me-your-work 技能记录的轨迹。
- `status.md` 在每次清空时由 `units.tsv` 和 `ledger.tsv` 派生，绝不手工维护。应根据表格重新生成，而不是把事件叙述写进去。

#### 任务简报

你给代理的提示词是你唯一的产出，而草率的简报会在整棵树中层层放大为垃圾产出。每次派生都必须携带全部字段。无法填写的字段，意味着你还没有界定该单元的范围。

```
GOAL         one sentence, the outcome, executable by a stranger with no chat access
SCOPE        paths this unit may write; paths it may not; its exclusive worktree or branch
CONTEXT      pointers to files and PRs; upstream reports pasted in full when this unit
             depends on them, because workers cannot see siblings
ACCEPTANCE   checkable criteria, one per line
VERIFY       exact commands or the project's `verify-<app>` skill, plus known gotchas
TIMEBOX      rough cap on runtime; on expiry, return partial findings and stop rather than run on
FORBIDDEN    no PR retargets or merges, no rebase, no force-push, no fixes outside scope,
             plus unit-specific bans
REPORT       status, branch, head SHA, PRs, verdict, what you actually ran, deviations,
             suggested follow-ups
STANDING     <preferences.md pasted verbatim>
```

简报的篇幅应与单元匹配。只含一条命令的单元，应把模板压缩为一段文字，但仍需写明目标、范围、验证命令和报告格式。围绕两行改动的 4KB 模板，编写和遵循的成本都比改动本身还高。派生可以按存储路径引用常设指令文件。原样粘贴仅用于每次恢复。

子协调者的简报还需增加其轨道边界和单元列表、派生预算、清空协议，以及汇总格式（每个子代理：名称、状态、PR、head SHA、结论、一行说明，外加轨道状态和前沿变化量）。

依赖关系是上下文的中继，而不仅仅是排序。未声明的上游上下文会让工作者靠猜测行事。缺失字段即属于拒绝派生的情形。每个子协调者每个波次抽查一份工作者简报，与其所抽查的波次并行进行，绝不作为该波次之前的关卡。简报不合格时，停止该轨道，并修正子协调者的指令，而不仅仅修正工作者，因为简报质量在运行后期会衰减。绝不对简报进行续接链式恢复。应基于整合后的范围重新全新派生。

#### 步骤

1. **界定框架。** 将完成判定条件表述为可计数的形式（“全部 126 个单元已合并，每个单元在台账中验证为 `unit-test-verified` 或更高”）。量化范围：单元数、大致工作量、预计堆叠数，以及挂钟时间预算。如果单个代理能在该预算内完成，则到此为止，改为运行 Autonomous run。精简流程不得依赖其他文档的存在。它意味着直接在本会话中完成工作：在有帮助的地方使用普通工作者，内联验证，边完成边落地，且不使用下文的存储、登记册或试点机制。按预算安排落地时间。大约到预算的 70% 时，停止派生，并落地已验证的内容。按项目命名各轨道。存在争议的分解或单向门决策，需在试点前经过 arena 技能。框架只需呈现一次。可逆的准备工作无需等待即可推进。
2. **安装运行时。** 运行 `orch init`。通过 show-me-your-work 技能开启轨迹，在任何派生之前编写常设指令，并使用 `orch frontier set --repo <repo-dir>` 从现有 PR 初始化 `frontier.json`；当代码托管平台为 Origin 时，加上 `--forge origin`。
3. **试点。** 让一个单元走完整个流程：简报、工作者、验证、堆叠条目、台账记录、合并。试点的目的是在只花费一个代理（而非五十个）的成本下，检验简报模板、验证方案和单元大小是否成立。在任何扇出之前，根据试点证据修正契约。试点规模应与单元相匹配。对于几乎相同且成本低廉的单元项目，第一个单元即为试点，按普通单元运行，并将其验证命令内联，该单元落地后立即开始扇出。专门的试点流水线（独立的验证代理、审计关卡）仅适用于昂贵或新颖的单元形态；对于克隆单元，串行化的试点没有可供检验的内容，不需要它。
4. **扩展。** 派生一个滚动窗口的工作者，数量上限为进行中的子代理上限，子代理完成后随即补充。阻塞式批次要为每批中最慢的子代理付出等待代价。只有超过角色与部署位置一节中的单次清空阈值时，才派生轨道子协调者。每次清空后重新计算可就绪的工作。将上游报告中继到下游简报中。同级之间的通信只能向上进行。抽查简报的审计与其所抽查的波次同时进行，若审计失败，则阻止下一次补充，而不是当前这次。
5. **清空。** 在每个清空节点执行下文的队列纪律。
6. **落地。** 落地是持续进行的，绝不是终结阶段。集成从第一个已验证单元开始，并与其余波次并行进行。在大型仓库上，stacker 从第一波次起即为常设角色，随单元验证而集成。在本地 git 操作成本低的仓库上，协调者依据角色与部署位置一节自行落地已验证单元。在处理上层堆叠工作之前，保持前沿为绿。以堆叠安全为准。只有在合并或报告新的 head SHA 时才推进 `frontier.json`。
7. **收尾。** 清空最后的收件箱，将每个已派生的代理对账至终态行（done、abandoned、zombie-reconciled），在真实产物上确认判定条件，确认每个已落地的 PR 都有针对其当前 head SHA 的结论，依据 show-me-your-work 审计轨迹（包括其跨模型审查），将反复出现的修正写入 `preferences.md` 或简报模板。保持存储完整无损，它就是事后复盘材料。

#### 队列与清空

- 收到完成通知时，运行 `orch inbox push <agent> <unit> <status> [--report PATH]`，然后回到原来的工作。绝不在行内进行深度审查。需要审查的完成项会变成一个验证者单元。绝不在清空过程中审查 diff。
- 在四个节点分批清空：关键区段结束时、轨道汇总时、前沿监视器被唤醒时（通过 loop 技能启动，并以较长的心跳作为后备），以及向人类汇报之前。每批以 `orch inbox drain` 开始。清空过程中到达的内容等待下一批处理。
- 需优先完成的关键区段：编写简报、堆叠操作、冲突决策、编写关卡、更新台账或前沿。
- 每次清空都会对每个指针分类（landed、needs-verify、failed、zombie、noise），通过 `orch unit add`、`orch unit set` 和 `orch ledger record` 写入对应的行，运行 `orch status`，然后在一条消息中派生下一波次。
- 在轨道汇总时对每个已派生的子代理作出说明：已到达、已重新派生，或其范围已被明确吸收。悄无声息地重做缺失子代理的工作，会同时掩盖浪费的开销以及其结果原本要弥补的覆盖缺口。
- 每次清空回合以 `orch status` 输出的三行结束：各状态的计数、发生了什么变化、仍开放的关卡。详细信息存放在 `status.md` 中。完整的回复约定适用于检查点和收尾阶段。

#### 堆叠安全

- 前沿是计算得出的对象，绝不是叙述性文字。每次合并和堆叠变更后都要重新计算 `frontier.json`：有序的 PR 列表、分支名、head SHA、代数编号，以及最低的未合并 PR。该命令沿当前检出分支遍历 PR 的 base 链，因此链的顺序和 PR 状态来自代码托管平台。默认使用 `gh`。当项目将代码托管平台解析为 Origin 时，传入 `--forge origin`。Head SHA 来自本地分支引用，因此应在 stacker 的克隆中解析。没有 PR 的分支会报错，而不是去猜测。
- 每个堆叠中恰好只能有一个 stacker 修改拓扑结构（链式 rebase、强制推送、base 重定向、合并），并在其堆叠内串行执行。将持有者记录在常设指令中。
- 工作者绝不 rebase，也绝不重定向或合并 PR。Babysitter 遵循 `playbooks/babysit.md`，每个堆叠一个，限定在一个不可变的前沿代数内。它们将冲突报告给 stacker，而不是自行 rebase。
- 关闭 PR 和重定向只能通过 stacker 进行。关闭某个 base PR 会使其上方的每条链成为孤立链。合并和堆叠手术与其他单元一样，都有各自的简报。
- 设置一个回顾监视器，跟踪已合并的 PR，关注回滚、合并后 CI 失败以及被孤立的后续工作。

#### 验证

验证应与单元相匹配。当 VERIFY 只是一条廉价的命令时，工作者运行它并报告输出，协调者抽查回执。专门的验证代理（使用与工作者不同的模型系列）仅适用于验证成本高、需要判断力或影响范围大的单元。如果验证代理的全部产出只是重新运行一条命令，那就是繁文缛节，而不是验证。

使用 `orch ledger record` 写入台账行。使用 `orch ledger check` 检查当前 PR 和 head SHA。`ledger.tsv` 每个结论一行，以 PR 编号加 head SHA 为键：`live-ui-verified | unit-test-verified | type-check-only | verifier-blocked | verifier-failed`。CI 通过是结论的一项输入，而不是结论本身。行为类工作需要优于 `type-check-only` 的验证。`verifier-blocked` 不算通过。环境恢复正常后重新派生。`verifier-failed` 应交给修复单元，而不是重新验证。工作者可以自我报告。验证者可以在同一键上覆盖其结论。新的 head SHA 会使该行失效，因此在重新堆叠后需重新验证。台账回答的是“是否经过验证”，而不是记忆或对话记录。

单元在落地的那一刻就必须将其产出外部化，绝不能推迟到运行结束时批量处理，否则它不算完成。工作者推送其分支，验证者写入台账行，回执存入存储。只存在于某个代理的 worktree 中的工作，在该代理死亡时就等于从未完成。

#### 存活性与故障

- 绝不为了检查代理状态而恢复它。恢复操作会重新启动一个空闲代理。应以只读方式探查：台账、`units.tsv`、`gh`、已推送的分支。对话记录的修改时间不代表存活。
- 无声死亡的代理会在收件箱中获得一条模拟的事后复盘行（单元、故障模式、最后的证据、可选方案）。证据到达时即根据证据重新规划。绝不等待完全静止。
- 按模式重试：触及上限或内存不足（oom），以更小的范围重新派生。网络中断，原样重试。工具错误，换用其他模型重试。未知原因，重试一次。重试两次后，放弃该单元并围绕它重新规划。
- 延迟数小时才返回的僵尸代理，在接受任何内容之前，须先与当前前沿和台账对账。通过新的单元挽救其独有的发现，绝不盲目合并。
- 当继续派生会在整棵树范围内产生垃圾产出时（上游输出有误、验收标准失效、基础设施瘫痪），在常设指令顶部写入停止线，让进行中的工作完成，修复根因，然后清除停止线。
- 对自身基础设施的重试，与限制子代理重试采用同样的上限。连续数次工具中止后，停止重试。将终态交接写入持久状态（已完成的内容、存放位置、确切的恢复命令），然后结束运行。
- 重启之后：运行中的代理已死亡，已推送的分支和存储仍然存活。重新读取常设指令和 `units.tsv`，重新计算前沿，按 PR 和分支而非代理 ID 重新关联工作，根据存储的简报加当前状态，为每个轨道重新派生一个子协调者，清空，恢复。已失效会话的存储锁会在下次写入时自行清除。`orch` 会替换持有者 pid 已不存在的锁。

#### 升级

需要交由人类处理的事项，应汇总到状态页中，而不是逐项提出：不可逆的操作（强制推送到共享分支、部署、删除、关闭他人的 PR）；没有任何实验能够解决的真正的产品或偏好决策；与观察到的实际情况相矛盾的常设指令；经过重新规划后仍然存在的项目级死胡同。提问之前，先将每项记录为 `gates.md` 条目，并围绕它安排其他工作。

以下事项绝不交由人类处理：前沿推动、rebase 操作细节、重试、CI 偶发失败分诊、审查线程分诊、格式修复、简报已经禁止的范围（拒绝并继续），以及“我是否应该继续”。存疑时，行动并记录日志。

运行中途的发现只修复阻塞前沿的部分，其余一律记入后续事项。在这种扇出规模下，哪怕是很小的范围泄漏也会倍增为没人要求的 PR。

**回复：** 在检查点和收尾时：判定条件及根据 `units.tsv` 和 `ledger.tsv` 得出的对应计数、各轨道及其各自落地的内容、前沿（PR 列表加 SHA）、结论摘要、已放弃的内容及原因、等待人类处理的关卡（仅此为需要人类做的请求）、存储路径，以及轨迹路径。数字取自表格，而非叙述。附上 PR 链接。
