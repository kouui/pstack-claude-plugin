### Trace 取证

**你要基于产物自己给出诊断。**

与**运行时取证（Runtime forensics）**不同，后者会对正在运行的进程进行插桩。这里的捕获数据已经存在。该产物是一份固定的数据集，读取它即可，不要重新运行。工具保持通用：使用 DevTools 或 trace 解析器处理 cpuprofile 和 `.json.gz`，使用文本编辑器处理 spindump，使用你的堆分析工具处理 heapsnapshot。

1. 识别格式，并用合适的工具加载它。大型产物在子代理中解析（即 **principle-guard-the-context-window** 技能），并在主线程中保留精简后的结论。按照 Subagents 章节的要求，为每个子代理选择其推理级别，以及快速或标准速度来完成工作。
2. 将原始产物转换为可查询的形式。把 trace 或堆快照转储到 sqlite 中，每个采样、帧或节点一行。在阅读之前先达到可查询的形态。
3. 收窄到根因。查询占用时间最多的帧，沿调用树走到热点路径。对于内存泄漏，从泄漏对象出发沿保留链追溯到 GC 根。对于 spindump，找到处于 on-CPU 或阻塞状态的线程及其等待原因。
4. 归因到源代码。通过产物自带的符号，把热点帧映射到文件、符号和行号。没有源码映射的帧还不是诊断。要么解析符号，要么明确说明该产物不包含这些符号。
5. 如果有成对的捕获，比较前后两份产物来确认。否则，将该结论标记为产物所支持的最强假设，而不是已确认的根因。
6. 交回一份带引用的诊断，除非被要求，否则不要给出修复。一旦根因确定，转交给 Bug fix 或 Perf issue 流程。吞吐量检查点保持一行：`throughput checkpoint: n/a, read-only forensics`。

**回复内容：** 产物及其格式、精简后的结论、源码位置、产物路径，以及成对的捕获是否确认了该结论。
