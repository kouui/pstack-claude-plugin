### Hillclimb（爬山法）

**你负责指标和实验的完整性。进行监督和审查。把具体的尝试工作委派出去。** 用于围绕一个可度量的目标，对某一事物进行持续的迭代改进。一次性修复属于 Bug fix 或 Perf issue。本流程即为循环。

核心纪律：一次变更，一次测量，保留或回滚。永远不要叠加未经测试的变更，也永远不要仅凭代码检查就宣称取得了改进（**prove-it-works** 原则型 skill）。

1. 在选定指标之前，先摸清工作负载与架构。对目标运行 **how** skill，列出可能改变结果的真实工作负载维度（数据规模、历史、状态、并发），并选择一个能复现用户抱怨的用例。如果没有任何用例能复现，就先修复复现方式，而不是开始爬山。然后确定一个指标、判定"更好"的方向，以及一个可检查的停止条件：该条件将目标与最少尝试次数的下限配对，使早期的侥幸胜利无法结束整个运行（例如"比基线至少提升 50%，且至少迭代 10 次"就是这种形式）。如果用户给出了数字，就使用用户的数字，否则与其协商确定。
2. 构建测量工具，验证其灵敏度，然后冻结它（**build-the-lever** 原则型 skill）。运行形成对比的真实工作负载，确认目标用例能复现症状，而较简单的用例能按预期区分开来。如果该工具无法区分它们，就修订工作负载或指标。在冻结之前，使用 **benchmark-checklist** skill 审查该工具，并让它输出其错误数量以及所完成工作的计数。冻结之后，一条可重复执行的命令输出指标，且采样量足以克服噪声（取 N 次的中位数，而非单次运行）。在进行任何变更之前，记录基线指标以及回归门禁（必须持续通过的测试）的一次通过结果。
3. 通过 **show-me-your-work** skill 打开决策日志。`decision.tsv` 每次尝试一行：id、假设、变更、before、after、delta、tests、verdict（保留或回滚）、note。每次尝试之前都要先阅读它。将其保留在代码树之外（已加入 gitignore）。
4. 让每个假设都基于步骤 1 中的架构模型，使其指明具体机制（"把 X 从启动路径上移出去，因为它阻塞首屏渲染"），而不是"试试对某物做缓存"。对于性能指标，按照 Perf issue 流程（`playbooks/perf-issue.md`）步骤 2 中的性能准则对假设排序。只借用其排序，不借用该步骤的停止规则。
5. 循环，每次迭代只验证一个假设：
   - 使用你配置的爬山模型（默认 `sonnet high`）将变更交给一个子代理，并限定范围。按照子代理一节的规定，为每项任务选择各子代理的推理级别以及快速或标准速度。监督并审查 diff，而不是亲自敲写（**guard-the-context-window** 原则型 skill）。当存在多个相互独立的有效假设时，将它们分派给并行子代理，每个子代理位于各自的 worktree 中（**separate-before-serializing-shared-state** 原则型 skill）。
   - 使用冻结的工具在变更前后进行测量，并运行回归门禁。
   - 只有当指标越过噪声范围且门禁保持通过时才接受变更。否则完整回滚该变更。一个"可能有帮助"的小调整不予保留。
   - 每个被接受的修复对应一次 commit，且只暂存你修改过的文件（`git add <files>`，永远不要使用 `-A`）。无论保留还是回滚，都要记录该行。
   每次迭代在下一次开始之前都要以一次检查结束（**sequence-verifiable-units** 原则型 skill）。如果运行是无人值守的，只借用 Autonomous run 流程（`playbooks/autonomous-run.md`）中的唤醒机制，不借用其停止规则。
6. 突破第一个平台期。陷入停滞时，连续多次被拒绝，就切换类别、组合接近成功的方案、重新阅读源代码，或尝试更激进的做法，然后再判定山已爬到顶。正确性和简洁性优先于数字。回滚破坏行为的胜利，保留在数字不变的前提下使代码更简单的改动（**laziness-protocol** 原则型 skill）。
7. 当停止条件满足时停止，或当剩余想法边际价值低且不值得其成本时停止。不要为了达成目标而放宽停止条件，也不要在仍有低成本未尝试的假设时放弃。如果陷入僵局，应将其上报，而不是空转。
8. 运行 **Opening a PR**，并按落地顺序把已接受的 commit 堆叠在一起提交。

**回复：** 指标与目标、基线到最终值及百分比变化、迭代次数（保留与回滚的数量）、每个被接受的修复各占一行、`decision.tsv` 的路径，以及如果继续推进你会尝试的最佳下一个想法。
