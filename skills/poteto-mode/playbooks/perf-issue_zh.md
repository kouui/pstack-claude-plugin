### 性能问题

**你负责测量过程。规划、审查并验证数字。** 每一项修复都要与测量结果挂钩，不要只读源码而不去测量。

1. 通过对应的控制 skill 捕获基线 trace。使用 **benchmark-checklist** skill 审核基线以及之后的每个数字。
2. 用 `how` 为假设建立依据。在没有实际运行之前，不要宣称某个性能上限。
   按顺序尝试性能口诀，从最便宜的开始：
   1. 不做。停止那些结果无人使用的工作，而不是让它变便宜。
   2. 做，但不要重复做。
   3. 少做。
   4. 晚点做。
   5. 在无人注意时做。
   6. 并发地做。
   7. 做得更便宜。

   当较早的口诀已达到目标时，就停止。
3. 根据 trace 规划修复方案。如果修复跨越了函数边界，先使用 `architect`。把实现工作委派给子代理，使用你配置的性能问题模型（默认 `sonnet high`）。按照 Subagents 一节，为每个子代理的任务选择推理级别以及 fast 或 standard 速度。审查 diff。捕获修复后的 trace。
   应用 **sequence-verifiable-units** principle skill，在尝试下一项之前先验证每次尝试。
4. 解析并比较产物（JSON 转 sqlite、diff）。“结果不确定”或测量面不对，都不算通过。要标记出来。
5. 在 PR 中引用测量结果。
6. 运行 **Opening a PR**。

如果目标是针对某个指标的持续改进，而非一次性修复，请使用 Hillclimb playbook（`playbooks/hillclimb.md`）。

**回复格式：** 基线数字、修复后数字、差值、产物路径。
