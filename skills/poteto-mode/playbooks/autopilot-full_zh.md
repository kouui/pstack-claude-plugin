### Autopilot-full

**你对裁决负责，不对 PR 负责。每个 PR 由一个负责人从构建带到合并，在你的 swarm（它从未编写过这些代码）证明落地的代码没有问题之前，任何东西都不能合并。**

一个裁决只覆盖一个 patch，绿色的 CI 只覆盖一个 head。第 4 步只在整体运行一次完整 swarm，只有重大变更时才再次运行。`playbooks/shipping.md` 中的 patch-id 规则可以承接某条 lane 的结果，但每个新 head 都需要自己的绿色 CI。

1. **先满足操作者的闸门。** 授权只覆盖队列中的条目，因此操作者指定为归其所有的条目以及队列之外的 PR，都止步于 merge-ready。要求说明计划不等于批准。
2. **为每个 PR 分派一个负责人，并让其工作位于替换者能够找到的地方。** 为整个项目一次性确定代码托管平台。GitHub CLI（`gh`）是默认选项。如果 `command -v origin` 成功，且 Origin 能够解析该仓库，则所有 PR 操作都使用 `origin pr`。否则继续使用 `gh`，并记录回退情况。绝不能要求使用 Graphite（`gt`）。每个负责人都是一个 Cursor 云端 agent，它按照 `playbooks/opening-a-pr.md` 构建并开启 PR，在真实产物上证明变更，按照 `playbooks/babysit.md` 将其维护到绿色，并在第 4 步和第 5 步通过后合并。

   尽早开启 PR，让 CI 和机器人与工作并行运行。代码只有在经过 slop-strip（`deslop` skill（`/deslop`））和 `/no-comments` 检查之后才算就绪，因此完整 swarm 运行的是已完成的代码。然后 rebase 到当前 trunk，并在自证之前报告 code-ready head，使验证运行在 patch 将要落地的基线上。之后的每个 head 都要报告，并在自证、CI 和 babysit 完成后报告为 merge-ready。除非 trunk 发生冲突或破坏了 CI，否则修复轮次都停留在该基线上，因为每次 rebase 都会重启 CI。在 code-ready 推送之前，以及在需要验证者的后续推送之前，在已提交的 head 上为受影响的路径运行仓库的检查。

   假设 VM 会崩溃。开始后不久，推送并在根 agent 的存储（路径见系统提示）中按照 **show-me-your-work** skill 开始一份决策记录，之后每个值得保留的单元完成后都要推送。派生子 agent 的一方要在该存储中记录其 id、状态，以及根据同类过往运行得出的 stuck-after 运行时长，以便在父 agent 崩溃时，根可以探查它。只对自己的分支执行强制推送，使用 `--force-with-lease`，并固定到你最后一次推送或接管的 SHA；对于任何不是你做出的推送，都要停止并报告给根。
3. **负责人在 trunk 上并行运行，绝不堆叠，** 使每个 PR 都能独立落地。
4. **进行一次 swarm 验证。** 完整 swarm 只在 code-ready head 上运行一次。只有新行为、重新设计或大规模新增差异时，才再次运行完整 swarm。rebase、合并冲突解决或小修复，只在新 head 上安排一个验证者。按照 **swarm** skill，在 code-ready SHA 上扇出独立的验证者。它们重新运行检查，通过其控制 skill（例如 `cursor-team-kit` 中的 `control-ui` 或 `control-cli`）或指定的驱动程序，在真实表面上实时证明承载关键行为的部分，并审计差异。若没有实时 lane，或者在审计 merge-ready 报告的凭证之前，裁决都不算干净，因为没有哪条 lane 会信任它未曾核实的声明。

   将每个已证实的发现（无论 lane 将其标记为何种级别）在一次 fix-forward 中发送给负责人，并为存在相同缺陷的每个位置编写一个红色测试。trunk 中存在、与 PR 无关的缺陷记录在 trunk 名下，不阻塞该 PR；但 PR 复制或新近触及的缺陷则归属于该 PR。绝不由你自己推送修复，因为每个分支只能有一个写入者。若负责人停滞，则替换它。
5. **负责人只合并你已验证的内容，并在其将落地的 trunk 上进行测试。** 绿色 CI 本身永远不能授权合并。一旦 swarm 的各条 lane 已经启动，合并准备工作就要 rebase 到当前 trunk，报告新 head，并等待绿色 CI。

   在合并之前，获取 trunk 并判断其变更是否会影响该 patch，因为为 trunk 的每次移动都进行 rebase 永无止境。当会落地的代码从未经过测试时，例如出现冲突、某个文件被双方同时修改，或者 PR 要运行的检查发生变化时，就要 rebase 并等待 CI。当双方都修改了 lockfile 时，若冻结安装在合并结果上通过，且 PR 变更的包在合并结果上的解析与在 head 上一致，则无需 rebase，因为该安装测试的正是将要落地的 lockfile；若安装失败，则 rebase 必须修复它。当 trunk 修改了 patch 的调用方，或 patch 所依赖的内容（例如它调用的代码或依赖版本）时，要在合并结果上运行该 patch 的检查，通过后再合并。否则直接合并。如果 trunk 迫使合并准备阶段之后出现第三次 rebase，则暂停并报告给根，由根安排相互冲突的工作顺序。
6. **运行根层。** 任何放宽闸门的事项，例如提高预算或加入允许列表条目，都需要验证者的证明，然后再由你重新背书，因为负责人是希望变绿的一方。在授权涵盖审批的情况下，该背书即为审批，负责人的记录应指向你的背书，供 lane 核查。被禁用或软失败的检查必须全部移除，因为它不再守护任何情况。绝不授予或绕过代码托管平台强制执行的审批，因为任何背书都无法覆盖它。

   操作者下达 go 指令后，启动 `/loop 1h`，持续审计，直到不再有委派的工作，因为长时间运行会偏离方向，而 agent 也会悄无声息地停滞。每次 tick 都要从 trunk 重新读取本 playbook 并修正偏差，例如未报告的 head 或未记录的 agent，方法是让其负责人进行记录，因为偏差是记录上的缺口，而不是停滞。它会探查每个 agent，直至最底层的叶子 lane，并根据其副作用而非状态文本或摘要来判断，因为后者可能掩盖卡住的子 agent。当一个 agent 出错、无法开始轮次，或在超过其 stuck-after 运行时长后仍无任何新动静时，它即为停滞；到第一次 tick 时，既未推送也未写入记录行的负责人同样视为停滞。正在等待你或操作者回应的 agent 不算停滞，因此要予以回复。立即替换停滞的 agent，而不必等待其停止操作完成。若某次 tick 改变了某些需要操作者知晓的内容，则按照 **ketchup** skill 向操作者汇报；若什么都没有改变，则保持安静。
7. **操作者一旦下达停止指令，立即停工。** 暂停会向每个负责人发出零写入指令。每个负责人都要报告其当前状态，并保留其任务简报，直到操作者解除。

**回复：** 按照 **ketchup** skill 向操作者汇报情况，涵盖每个 PR 的状态和裁决、已合并的内容、背书及其原因，以及尚未解决的操作者闸门，并附上每个 PR 和记录的链接。
