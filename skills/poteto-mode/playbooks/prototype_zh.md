### Prototype

**你负责设计决策，而不是代码。原型是一次性的工具。真正的构建要在 Feature 之后进行。**

这是唯一一个 Laziness Protocol 的“最小改动”和验证标准会反转的 playbook。追求速度而非打磨，代码质量无关紧要，也不做规划。严谨性体现在低成本地选出正确的设计。提出用户没有要求的变体，丢弃一种方案并尝试另一种。

1. 明确原型要做出的决策：选哪种布局、哪种交互、哪种密度；如果是经验性分叉，则选哪种行为、时序或方法。没有待决策的问题就不需要原型。转交 Feature。
2. 当设计空间开放时收集参考资料。搜索已有的先例，总结主题、配色和布局的情绪板，在构建前让用户选择方向。方向已定时跳过。
3. 在隔离的临时目录中构建一次性产物，与生产源码分开。对于视觉决策，使用原生 HTML/CSS/JS 或能渲染该想法的最轻量技术栈，依赖使用 CDN，并配合支持热重载的开发服务器。对于行为或时序决策，使用能验证该问题的最小脚本。不使用生产框架，不写测试，不做抽象。
4. 比较多个方案时，将它们放在同一个切换器后面（按钮或按键），每个变体都要加标签。这是 **exhaust-the-design-space** 原则 skill 在低成本下的体现。
5. 在对应的表面上验证。对于视觉决策，通过 control skill 为每个变体截图并驱动交互。对于行为或时序决策，通过记录时序、打印输出或观察渲染结果来观察你要决定的东西。这里的观察本身就是测试，而不是断言。
6. 呈现各方案、权衡取舍和建议。输出是决策加上一次性产物，而不是可交付的代码。将选定的方向交给 **Feature**（或由 `architect` 决定结构），进行真正的构建。

**回复内容：** 探索过的变体、证据（视觉决策使用截图，行为决策使用观察到的输出或时序）、权衡取舍、你的建议，以及临时目录路径。明确说明该原型是一次性的。
