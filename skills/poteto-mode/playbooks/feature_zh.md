### Feature

**你负责设计。规划、评审、验证。** 委派实现工作。留在主导位置。

1. 对受影响的子系统使用 `how`。
2. 使用 `architect` 进行并行设计探索。
3. 将吞吐量检查点写成四个待办项。如果某个维度确实不适用（单文件、无扇出），该项保留并写上 `n/a: <reason>`，不要删除：
   - **阻塞性的第一步。** 在扇出之前先运行门禁。
   - **独立工作流。** 不相交的文件、服务或层可以并行。共享写入必须串行。
   - **共享可变状态。** 默认拆分目标（**separate-before-serializing-shared-state** 原则技能）。只有存在真正的不变量时才串行。
   - **最小安全分解。** 如果一个工作者最合适，说明原因。
4. 使用你配置的 feature 模型（默认 `sonnet high`）将代码编写委派给子代理，并给出明确的范围（文件路径、按照 **principle-model-the-domain** 命名的数据形状及其组织结构、用状态机而非分散的布尔值、用表/注册表而非分支、用类型化模型而非反复假设形状、在委派者编写逻辑之前选定，以及成功标准）。按照子代理部分的规定，为每个子代理选择适合该工作的推理级别以及快速或标准速度。当实现存在多种有效形状（错误处理、抽象层、测试结构）时，改为通过 **arena** 技能委派，使运行者提出备选方案，并由交叉评审守住选择。这一点是强制的：不允许以"跳过并给出理由"作为例外，Laziness Protocol 也不能覆盖它（收益在于评审分离，而不是节省代码行数）。被禁止生成子代理的子代理，通过以同样的评审分离直接负责该 diff 来满足此要求。不要出现等待嵌套代理的"待命"回复。注释遵循 **Comments**。只做精确编辑，对于源自上游的文件，要重新对照源文件校准。将共享原语的改进移植到所有使用方并分别验证。频繁提交。
5. 在对应的表面上验证。"无法确定"或表面不匹配不算通过。须标记出来。
6. 变基为小型、有序的提交。后续工作以堆叠方式提交。
   使用 **sequence-verifiable-units** 原则技能，在开始下一个单元之前，先构建、验证并提交每个小单元。
7. 如果设计存在争议，在发布前使用 `interrogate`。
8. 运行 **Opening a PR**。

与代码强耦合的工作（一个功能、一次迁移）交给单一负责人，并内联检查点。该负责人在阻塞阶段之后在内部进行扇出。父级扇出仅适用于能产出独立产物的切片（审计、跨子系统调查、相互竞争的实验）。在阶段边界处重写检查点。生成新的负责人，而不是串联中断。

**回复：** 你构建了什么、选择了什么以及为什么、吞吐量检查点、未决决策。设计备选方案使用表格。
