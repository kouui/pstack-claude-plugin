### 重构

**你负责契约。结构会改变，行为不会改变。** 这与新增功能（Feature，会增加行为）和缺陷修复（Bug fix，会修正行为）不同。

如果清理过程中发现缺失的功能或真实的缺陷，请将其拆分出来，先针对已固定的契约提交结构性变更。允许进行重新设计，但必须明确命名，并转交给 Feature 流程。大型或跨领域的结构性工作属于 **figure-it-out** 技能的范围。本playbook处理的是聚焦到中等规模的变更。

1. 先固定行为契约。对受影响的子系统运行 **how** 技能以了解契约，然后在任何结构调整之前，编写特征化测试、快照或等价性验证工具，以捕获当前行为。如果该区域没有测试覆盖，请先编写固定契约的测试，再动结构。类型检查和 lint 不能作为固定契约的依据。
2. 依据 **principle-model-the-domain** 指出代码缺少的结构。当形态已经清晰且局部时，保留简单的代码。重新塑形必须删除分支或无效状态，而不是增加间接层。
3. 明确目标形态。说明如果今天从头构建，模块布局、类型和调用图应当是什么样（**principle-foundational-thinking**、**principle-redesign-from-first-principles**）。如果目标跨越函数边界，在移动之前运行 **architect** 技能，对形态进行并行的设计探索。
4. 先减后加。在引入新形态之前，删除死代码、折叠只有一个调用方的包装函数、去掉冗余的校验器，并移除孤立的引用（**principle-subtract-before-you-add**）。交付能达到目标形态的最小变更（**principle-laziness-protocol**）。"也许有帮助"的投机性清理会被回退。
5. 以小步、保持行为不变的方式推进，每一步都要让固定的契约保持通过。对于 API 重塑，在同一波次中迁移所有调用方并删除旧 API（**principle-migrate-callers-then-delete-legacy-apis**）。不要使用兼容性垫片，也不要保留新旧并行的路径。对照实际文件逐一核查每次重命名。重命名常常会漏掉字符串、正文和反向引用中的用法。机械性编辑应委派给子代理，使用你配置的重构模型（默认 `sonnet high`），并限定明确的范围（文件路径、被移动的名称、需要保持的行为）。请按照 Subagents 一节的规定，为每个子代理选择推理级别以及快速或标准速度。
6. 在真实产物上证明行为未变，而不是"它能编译"（**principle-prove-it-works**）。对于较大的重塑，运行等价性检查：例如一个对比新旧输出的脚本、对已记录基线在新代码上重放，或通过相关的控制技能在对应的表面上进行冒烟运行。
7. 确认该变更值得保留。成功的衡量标准是降低阅读者的负担（**principle-minimize-reader-load**）。如果该差异没有在某处降低阅读者的负担，就将其回退。
8. 将变更变基为小而有序的提交。先是减法提交，然后是重塑，最后是任何后续清理。使用 **sequence-verifiable-units** 原则技能来安排这些提交，使每个保持行为不变的切片在下一个切片之前保持通过。运行 **Opening a PR**。

**回复：** 发生变化的结构、你用来约束它的契约固定点、等价性证明、阅读者负担的变化、已交付的内容以及被回退的内容。不引入新行为。
