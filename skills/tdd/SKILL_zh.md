# TDD Bug 修复

当修复一个测试路径清晰且成本低的 bug 时，先在修改生产代码之前把错误行为变成可执行的检查。目标是编写一个聚焦的回归测试，它在修复前失败，在修复后通过。

如果添加测试不切实际，不要强行添加。如果可用的测试需要大范围的测试框架搭建、脆弱的 mock、缓慢的端到端基础设施、仅存在于生产环境的状态、模糊的复现步骤，或大量无关的 fixture 变动，则跳过新增测试，改用最接近且有用的验证方式。

## 工作流程

1. **理解 bug。** 确定预期行为、当前行为、受影响的路径，以及最小的可观察复现步骤。
2. **选择最窄的可执行检查。** 优先选择该代码路径已在使用的最接近的单元、组件、集成或回归测试。如果没有明显可行的测试路径，不要为了满足流程而从零创建。
3. **先写失败的测试。** 添加能捕获该 bug 的最小聚焦测试。测试应编码预期行为，而不是镜像当前实现。
4. **修复前运行新测试。** 确认它因预期原因失败。如果它因无关原因通过或失败，先修正测试或复现步骤，再编辑实现。
5. **修复 bug。** 做出最小的生产代码改动，使其满足预期行为，同时保持附近的契约不变。
6. **重新运行回归测试。** 确认测试现在通过。

## 如果无法编写失败的测试

改用最接近的可执行回归检查：有针对性的脚本、手动复现命令、浏览器自动化、快照对比、日志断言或聚焦的集成检查。

宁可不加新测试，也不要写坏测试。坏测试是指：主要测试 mock、编码了当前实现细节、依赖时序或无关的全局状态、为小修复需要昂贵的基础设施，或在证明修复后会被立即删除的测试。

## 约束事项

- 不要为了匹配错误的实现而修改测试。
- 除非预期行为确实发生了变化且原因明确，否则不要弱化现有断言。
- 让回归测试聚焦于该 bug。避免大范围的 fixture 变动或与之无关的覆盖率扩展。
- 如果 bug 是不稳定的（flaky），在可能的情况下让测试变得确定性，并记录所锁定的信号。
- 如果该 bug 暴露了更广泛的一类失败，先提交聚焦的回归路径，然后再考虑补充同级的覆盖。

## 最终回复

报告证据，而不仅仅是结果：

- 指出修复前失败的测试或可执行检查，以及它产生的失败信息。
- 指出修复后通过的测试运行，以及所做的相邻验证。
- 如果无法证明修复前的失败证据，说明原因，并描述所使用的最接近的回归检查。
