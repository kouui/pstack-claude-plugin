# 维护形式化验证 skill

在 Claude Code 中，每个会话开始时先阅读一次 [Claude Code 适配器](../../docs/harness/claude-code.md)，然后再按照本 skill 操作。它把 pstack skill 中的 Cursor 名称映射到 Claude Code。

形式化检查证明的是它所描述内容的某个属性。当代码发生变化而验证没有变化时，检查可能仍然通过，但它描述的代码已经不存在了。这种通过最危险，因为它看起来像一个证明。本 skill 是为 `/create-formal-verification-skill` 生成的 verify skill 所用的维护循环，也适用于任何针对命名代码运行模型检查器、证明器或代码级验证器的项目本地 skill。项目本地 skill 处理的是代理在使用该 skill 时所做的变更。本 skill 处理的是那些绕过了它的变更：合并、未通过该 skill 进行的编辑，以及跨越多个提交累积的漂移。

## 结果

为每个检查给出一个结果，并说明是哪一个：

- **in sync**：自上次同步以来没有任何变更改变检查所描述的内容，且检查通过。
- **updated**：代码发生了变化，验证现在描述的是新代码，且检查通过。
- **bug**：验证描述的是当前代码，而代码违反了该属性。这是关于代码的发现，不是漂移。
- **blocked**：无法让检查恢复一致，或无法运行检查。准确说明原因。

一个检查可以同时是 updated 和 bug：更新使验证重新描述了代码，然后该属性在这份代码上失败。

## 编辑范围

只编辑验证相关内容：模型、harness、属性文件，以及 verify skill 本身。除非用户要求，否则在一次运行期间绝不编辑产品代码。当某个属性在当前代码上失败时，不要为了让它通过而削弱属性或模型。应报告该失败。

## 步骤

1. **找出检查。** verify skill 没有固定名称，因此要根据其功能来查找：即针对命名代码运行模型检查器、证明器或其他验证器的项目 skill。阅读你找到的每一个，或阅读用户指定的那一个。对每个检查，收集其属性、所覆盖的代码、边界与假设、运行它的命令，以及最近一次被确认能描述当前代码的提交。如果不存在 verify skill，则停止并指向 `/create-formal-verification-skill`。如果该 skill 没有记录同步提交，则使用最后一次修改验证文件的提交，并说明你这样做了。

2. **按原样运行。** 在做任何修改之前，先将每个检查运行一次，并记录结果。这里的通过并不能说明代码是正确的，它只说明旧的描述仍然成立。这里的失败可能是漂移，也可能是 bug。在第 5 步之前不要判定是哪一种。

3. **阅读对已覆盖代码的每一项变更。** 对比从同步提交到当前提交的已覆盖文件，并阅读每条提交信息。同时查找发生了移动的代码：被重命名、拆分或移动到其他文件的已覆盖函数，仍然属于已覆盖代码。还要查找触及某个检查所守护状态的新代码，例如一个写入相同字段的新函数。对每项变更，判断它属于以下哪一类：
   - **无影响。** 该变更不改变验证所描述的任何内容，例如格式调整、注释，或验证未覆盖的代码路径。请对照模型或 harness 来核实，而不是依据提交信息。
   - **验证不再描述代码。** 原本不可分割的一个步骤现在变成了两个，某个分支被添加或删除，某项检查被移动，一条新路径能够到达受守护的状态，或某个值现在有了不同的取值范围。模型或 harness 必须修改。
   - **承诺是有意改变的。** 该变更改变了代码所做的承诺，并且变更中的证据表明这是有意的：文档注释、测试、变更日志或提交信息。属性必须随之修改，并且你必须引用该证据。
   - **承诺可能已被打破。** 代码发生了变化，但没有任何证据表明承诺发生了改变。将随之出现的失败视为 bug 候选。

4. **依据代码更新，而不是依据结果更新。** 修改模型或 harness，使每个发生变化的部分再次指向审阅者可以打开的代码，并保持代码中一个不可分割的步骤在验证中仍然是一个步骤。在重新运行之前，依据代码编写更新内容，不要根据什么能让检查通过来塑造更新。只有针对有意改变的承诺才修改属性。记录旧的措辞、新的措辞以及证据。除非变更使边界变得错误，否则保留边界。如果必须缩小某个边界，请在报告中说明。

5. **重新运行并判定每个结果。**
   - **通过：** 检查现在可能是在一份已经失去失败能力的描述上通过的。对新代码施加该属性所防范的破坏，例如删除一项新的检查，或调换一个新步骤的顺序，并确认检查能够捕获它。然后撤销该破坏。
   - **失败：** 对照真实代码逐步重放反例。如果某个步骤在代码中不可能发生，则验证有误。修复验证，并说明错在哪里。如果每一步都可能在代码中发生，则这是 bug。指出引入它的提交，用代码自身的语言将反例叙述为一系列步骤，并用一句话说明危害。如果一个低成本的测试或对真实代码的复现能够展示该 bug，请将其作为证据加入报告。不要将其提交到产品代码中。

6. **更新 verify skill。** 更新每个检查所覆盖的代码、命令、边界、假设以及同步提交。将同步提交设置为你所检查过的那个提交。对于 blocked 的检查，不要移动同步提交，并在报告中说明。然后像下一位代理那样完整地执行一次 verify skill，以确认其步骤仍然可以运行。

## 报告

针对每个检查，告知用户：

- 结果，以及你所阅读的提交；
- 验证中改变了什么以及为什么，并为每项改动给出简短理由：代码的形态发生了变化，或承诺是有意改变的（附证据）；
- 重新运行的结果，以及你用来证明更新后的检查仍然能够失败所施加的破坏；
- 每个 bug，用平实的语言说明：以代码语言书写的步骤形式的反例、危害，以及引入它的提交；
- 验证仍未覆盖的内容，包括应当覆盖却未覆盖的新代码。

明确指出哪些失败是验证的漂移，哪些失败是代码中的 bug。对于在更新之前通过、更新之后失败的检查，说明这次旧的通过是基于过时的描述。

将验证更新放入单独的变更中，与任何产品修复分开。
