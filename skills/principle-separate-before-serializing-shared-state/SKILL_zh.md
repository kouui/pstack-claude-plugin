# 先分离，再串行化共享状态

当并发的参与者可能共享可变状态时，先问它们是否真的需要同一个可变对象。如果不需要，就消除共享。当共享确实存在时，在结构上强制串行化：锁文件、顺序阶段、独占所有权。说明和约定不是并发控制。

**原因：** 对共享状态的并发写入会产生竞态条件，这类问题时有时无、难以复现，且调试成本高昂。

**模式：**
1. **识别共享的可变状态**（双方都读写的文件、双方都推送的分支、双方都定义和使用的 API）。
2. **默认做法：消除共享的写入目标。** 问自己：这些参与者是需要一个统一的规范对象，还是只是在发布彼此独立的事实？为每个参与者分配其专属拥有的文件、键、分支或状态目录，并且只在读取或报告的边界处合并。让两个 worker 各自把自己的 `lastX` 字段写入同一个 `state.json`，仍然是共享写入。`indexer-state.json` + `metrics-state.json` 则不是。
3. **只有当一个共享写入目标是真实的不变量时，才在结构上串行化访问**（锁文件、顺序阶段、单写入者 actor，或原子比较并交换）。把"我们需要一把锁"视为需要检查的设计坏味道，而不是默认答案。
