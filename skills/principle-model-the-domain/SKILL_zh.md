# 对领域建模

用数据结构编码真实的领域，而不是把领域规则分散在各处的条件判断中。与领域匹配的结构能让非法状态无法表示，并删除分支。在编写时选择它成本很低；之后再去恢复它，就变成了重构，而且常常被推迟。

适用场景：

- 用状态机代替分散的布尔值、阶段或生命周期检查。
- 用类型化模型代替松散的参数或重复的形状假设。
- 用映射表、注册表、查找表或可辨识联合代替分散在多个文件中的分支。
- 用 reducer 或 command/event 模型代替临时的状态变更。
- 围绕同一套领域知识组织模块，而不是按加载、校验、转换、保存这样的步骤顺序组织。执行顺序不等于所有权。
- 用小型模块边界收拢重复的行为、所有权或不变量。
- 当访问模式需要时，使用队列、缓存、索引、图、树或规范化集合。
- 任何其他合适的结构。如果没有现成的结构合适，就弄清楚代码绝对不能允许什么、数据如何被读取，然后找到恰好能编码这些要求的结构。

不要强行引入抽象。如果当前结构已经清晰、局部，并且不太可能增长，就优先使用朴素的代码。对那些只增加间接层、却没有删除分支、重复规则、非法状态或生命周期风险的抽象，要保持怀疑。

你跳过了这一原则的迹象：新功能又在现有的 if/else 链上增加一个分支，或者出现第二个必须与第一个保持同步的布尔值。按时间顺序分解是另一个迹象。以阶段命名的模块会在各个步骤中重复同样的领域规则。
