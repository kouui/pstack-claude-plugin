# 创建形式化验证技能

在 Claude Code 中，每个会话开始时先阅读一次 [Claude Code 适配文件](../../docs/harness/claude-code.md)，然后再按照本技能操作。该文件把 pstack 技能中的 Cursor 名称映射到 Claude Code。

测试检查的是某人想到并写下的用例。形式化验证检查的是既定范围内的每一个情况：模型中每一种步骤顺序、有界范围内的每一个输入，或每一个输入。本技能会找到仓库中最需要验证的部分，验证其中的一项属性，并留下一个项目本地技能，使下一个代理能够依据该属性检查变更。要为一个冷启动、在变更中途阅读、且从未见过你工作内容的代理编写这个技能。用户必须能够信任结果并据此行动，而无需学习验证语言。

## 从代码中选择目标

根据代码回答问题，只询问你无法从代码中观察到的内容。如果用户指定了某个领域或某个 bug，就从那里开始。

好的目标是代码所作出的一项承诺：一旦被破坏就会伤害用户，而测试很少能覆盖到破坏它的情况。选择仓库中最强的此类目标，而不是最容易验证的那个。

## 让问题决定工具

选择以最低成本回答该问题的工具：模型检查器、证明助手、基于 SMT 的验证器，或其他工具。事件是否可能以错误的顺序发生，通常适合在设计的小模型上使用模型检查器，而 TLA+ 是任何语言中此类问题的默认选择。代码本身对所有输入是否都正确，例如内存安全、溢出或数据结构不变式，通常适合在代码上直接运行的验证器。如果该语言没有可运行的验证器，就直接说明，并用生成的输入测试真实代码，而不是对函数做手工建模。如果某项属性必须在任意规模下都成立，而有界检查不足以保证，则可能需要证明。优先选择仓库开发者能够安装和运行的工具，并向用户说明你选择它的理由。

## 优秀的标准

- **忠于代码。** 模型或证明的每一部分都指向评审者可以打开查看的代码。验证中被视为一个不可分割步骤的内容，在代码中也必须是一个不可分割的步骤。名称取自本仓库。
- **能够失败。** 一项从未见过失败的检查什么也证明不了。在保护该属性的代码的损坏变体上展示每项属性失败，例如移除某个检查或调换某个步骤的顺序。
- **发现保持为发现。** 当当前代码违反该属性时，要用代码自身的术语连同反例一起报告。不要为了让它通过而削弱属性或模型，除非用户要求，否则也不要修改产品代码。
- **诚实界定范围。** 说明验证了什么、在哪些边界和假设下验证、以及遗漏了什么。通过验证只说明模型或边界成立，并不代表整个系统成立。
- **不借助工具也能读懂。** 用一句平实的话分别说明属性和危害。用代码中的措辞，以简短的步骤序列描述反例。
- **便于重复运行。** 一条命令、可复现的工具版本，以及足够短的运行时间，使下一个代理能在每次相关变更时都使用它。
- **与代码保持同步。** 记录每项检查覆盖的文件和函数，以及你最后一次确认验证与其描述一致的提交。当被覆盖的代码在该提交之后发生变化时，下一个代理能够看出验证需要重新审视。

## 生成验证技能

编写一个项目本地技能，其 frontmatter 要写明领域名称并说明何时使用。没有 frontmatter，该技能就不会被注册。仅凭这个技能本身，下一个代理必须能够判断一项变更是否触及已验证的代码、运行检查、区分真实 bug 与建模错误，并在变更是有意为之时更新验证。把覆盖记录和同步提交写入技能中，并告诉下一个代理：只有在确认验证在新提交下仍然描述代码之后，才能将同步提交向前推进。使用本仓库真实的命令、路径和名词，不要留下任何占位符。

## 交付前先证明它有效

作为下一个代理，在一个确实会破坏真实代码中该属性的临时变更上，完整执行一次生成的技能。它必须能捕获到这次破坏。然后撤销该临时变更，并确认检查恢复到初始状态：通过，或仅因你将要报告的发现而失败。从未运行过的验证技能只是草稿。如果技能未能捕获破坏，或某个步骤没有运行，应修复技能或验证本身，而不是修改临时变更。

## 交接

告诉用户你验证了什么、使用了哪种工具以及为什么、边界条件、检查发现了什么（用平实的语言）、如何运行，以及它不覆盖什么。只有在你发现了相近的目标时，才建议第二个目标。如果有变更没有重新检查验证，请引导用户使用 `/maintain-formal-verification-skill` 使验证与代码重新保持一致。
