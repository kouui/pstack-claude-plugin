# 维护验证技能

在 Claude Code 中，每次会话开始时请先阅读一次 [Claude Code 适配器](../../docs/harness/claude-code.md)，然后再遵循本技能。它把 pstack 技能中的 Cursor 名称映射到 Claude Code。

功能地图会在应用发生变化的那一刻开始过时。本技能是对由 `/create-verification-skill` 生成的技能（或任何带有功能地图的项目本地验证技能）进行维护的循环流程。严谨性的单位是功能，而不是每一句话：从源码覆盖每个功能文件，并对每个功能进行实时演练，但不必把每个要点都逐一执行到底。

## 结果

选择其中一个，并说明选的是哪个：

- **clean** —— 每个功能都获得了源码和实时两方面的覆盖；没有值得交付的内容。不创建分支，不提交 PR。
- **changed** —— 一个 PR 交付已证实的文档、harness 或地图修正。
- **blocked** —— 覆盖无法完成，或已证实的修正无法安全交付。准确说明是什么阻碍了它。

## 编辑范围

只编辑验证技能自己的目录（其 SKILL.md、features/，以及它所拥有的任何 harness 脚本）。在一次运行期间绝不编辑产品代码：如果地图描述的某个行为，应用已经不再具备，那么这要么是文档漂移（修正地图），要么是产品回归（报告它，不要用文档掩盖）。

## 流程

0. **定位目标。** 找到要维护的验证技能：即其正文包含启动和驱动章节以及功能地图的项目本地技能（通常位于 `.cursor/skills/verify-*/`）。如果有多个候选，询问用户选哪个；如果一个都没有，停止，并指向 `/create-verification-skill`，而不是凭空编造目标。

1. **索引整理。** 阅读功能地图的 README，并枚举其同级文件。修复缺失、多余、重复或失效的条目。这一步很轻量，不生成通用清单。

2. **源码阶段。** 为每个功能文件分配一个只读子代理，并发启动。每个子代理解释"这个面向用户的功能是如何工作的？"，从源码给出分析，用引用标出可能的文档漂移，并返回一份简洁的实时验证方案。返回格式：功能摘要 / 源码入口点 / 可能的漂移或无 / 一份方案。

3. **对账。** 每个功能文件都必须有一份返回的摘要。将重叠的方案合并为尽可能少的应用状态。抽查被引用的漂移；不要重新证明已判定为干净的论断。扫描近期改动，找出地图中缺失的面向用户的界面，要求给出具体的源码路径后，才能认定其缺失。

4. **实时阶段。** 即使源码看起来干净，也必须执行。协调者负责所有驱动操作；遵循验证技能自身的启动模型：对于服务器和 UI，使用一个长期运行的实例并串行驱动；对于短生命周期的 CLI，每次驱动使用一个全新的隔离会话。由技能的启动章节决定，而不是由本技能决定。每个功能至少演练一次，并在整个阶段中始终守住三项不变量，无论发生什么失败：(1) 在自上次异常行为以来未经健康检查的实例上，绝不进行驱动——首次驱动前执行 doctor，在以会话为单位的每个新会话上执行 doctor，任何一次驱动失败后再次执行 doctor；如果 doctor 无法发现故障（例如进程健康但 UI 处于卡死状态），则重置到已知状态或重新启动，而不是寄希望于侥幸。(2) 迄今为止获取的证据在任何清理之后都必须保留，并在其命名位置进行检查，而不是默认假定。(3) 驱动启动的任何内容，都不得超出该次驱动的用途而继续存在——无论会话是卡住、已退出还是被共享，失败迭代遗留的残留物都要清理（对于共享实例，清理的是残留物，而不是实例本身）。如果 doctor 失败是由技能漂移引起的，那就属于漂移：在编辑范围内修复它，并重试一次——只重启修复所使本次修复失效的部分，不要多做——然后才能将本阶段判定为 `blocked`。只有当功能无法访问时，才可判定为 `verified-unreachable`，并且必须写明具体前提条件（认证、权限、操作系统、外部状态）以及尝试过的路径；如果地图遗漏了该前提条件，那就是漂移。任何来自分诊的 harness 修复，在交付前都必须经过实时重新驱动。最终清理在本次运行的最后一次驱动之后进行——包括那些重新验证的驱动——以确保运行结束时没有任何内容残留（证据按技能规定保留）。

5. **分诊。** 面向用户的描述错误或缺失 → 文档漂移，予以修复。harness 无法驱动但实际工作正常的行为 → harness 缺口，予以修复；harness 修复遵循与生成阶段相同的辅助脚本规则（脚本必须可执行，调用方式必须写在技能正文中）。应用行为确实已损坏 → 产品缺口；记录下来交给用户，并使其不出现在本次 PR 中。

6. **交付或停止。** 结果为 changed 时：提交一个包含已证实修正的 PR，并在此之前重新阅读每一个被修改的文件。结果为 clean 或 blocked 时：不提交 PR，如实报告结果和覆盖情况。

保留简明的运行笔记（已覆盖的功能、无法到达的前提条件、已确认的漂移、结果），存放在临时位置；不要提交这些笔记。
