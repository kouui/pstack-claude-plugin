# Notion 文档

## 本来源包含的内容

- PRD（产品需求文档）
- 技术规格与 RFC
- 架构决策记录（ADR）
- 设计评审的会议纪要
- 带有领域背景的团队页面
- 事故复盘（Postmortem）
- 可能解释防御性代码的 Runbook
- 设定优先级的战略文档

"为什么"往往在代码之前以长文形式存在于 Notion 中。一个重要功能通常都会有对应的文档。

## 如何搜索

使用 Notion MCP。

1. **使用 `notion-search` 进行关键词搜索。** 尝试：
   - 功能名称
   - 目标代码中的关键符号 / 类名
   - 作者账号（设计文档往往在代码落地之前就已撰写）
   - 错误字符串或用户可见的术语
   - 如果你知道代码发布的时间，使用限定时间范围的查询
2. **使用 `notion-fetch` 获取候选页面。** 阅读完整内容，而不是预览。理由常常埋在文档中间。
3. **追踪反向链接和子页面。** 设计文档通常有子页面，用于记录已考虑的替代方案、附录或实现说明。
4. **检查相关数据库。** `notion-query-data-sources` 和 `notion-query-meeting-notes` 可以找出讨论过该决定的会议纪要。
5. **搜索作者的个人空间。** 如果 PR 作者有个人笔记本（在某些公司很常见），其中可能保存着先于代码的探索性思考。

## 好的证据是什么样的

- 一份 PRD，其 "Problem statement" 或 "Motivation" 部分与目标代码的用途相符
- 一个 "Alternatives considered" 或 "Rejected approaches" 部分
- 一份事故复盘，明确指出目标代码是针对某个具体事故的修复
- 会议纪要记录了 "我们决定 X，因为 Y"，并且与 PR 的作者和日期范围相关联
- 一份填写得不平庸的 ADR 模板（status、context、decision、consequences）

## 常见陷阱

- **文档过时。** 规格往往在实现之前编写，之后不再更新。文档可能描述的是已经改变的计划。请与实际 PR 交叉核对。
- **文档与现实不一致。** 规格可能写着 "我们将做 X"，但代码实际做的是 Y。请标记这种偏差。综合者会指出这种矛盾。
- **样板模板。** 一些组织要求填写 "Why" 部分，于是被填入空话。要寻找具体的内容。
- **未被链接的文档。** 最相关的文档可能没有被任何地方链接。广泛的关键词搜索会有所帮助。
- **多个草稿。** 如果某个主题有多份文档，找出最终定稿或最近更新的那一份。检查日期。
- **访问受限的页面。** 如果无法访问某个页面，将其记为缺口。

## 返回内容

对于每份相关文档：
- 标题与 URL
- 作者与最后更新日期
- 动机文本（逐字引用），并注明页面/章节位置
- 相关的链接页面（以便综合者引用）
- 文档是定稿还是草稿
