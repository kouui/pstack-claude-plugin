# Linear 工单

## 此来源包含的内容

- 描述功能、缺陷及其动机的 issue
- 附加在 issue 上的项目文档（通常是 PRD 或规格说明）
- 父/子 issue 关系（宽泛的计划 → 具体的工单）
- issue 上的评论（澄清、范围变更、"我们为什么要做这件事"的理由）
- 标签（例如 `compliance`、`customer-request`、`perf`），用于标示动机类型
- 解释范围变更的状态更新
- 附件以及关联的 GitHub PR

Linear 通常保存着产品与业务背景：即"我们这样做是因为客户 X 提出了要求"或"这是为了 Q3 合规计划"这一层信息。

## 如何搜索

使用 Linear MCP。

1. **从关联工单开始。** 如果种子提交或 PR 引用了工单 ID（例如 `ENG-1234`、`[BUG-567]`），先用 `get_issue` 获取这些工单。阅读完整 issue，包括评论。
2. **按关键词列出相关 issue。** 使用 `list_issues` 对功能名、关键符号或业务术语进行文本搜索。尝试多种措辞。
3. **遍历 issue 树。** 如果你找到的是子 issue，就获取其父 issue。子 issue 偏战术层面，父 issue 通常承载"为什么"。
4. **阅读项目文档。** 如果 issue 属于某个项目，使用 `get_project` 并检查附加文档。规格和理由最常被记录在项目级文档中。
5. **检查标签和里程碑。** 标签提示动机的类别（customer-request、incident-followup、compliance）。里程碑将工作与截止日期关联，这往往能揭示动机。

## 有效证据的样子

- 陈述业务问题的 issue 描述："客户 Acme 因其 SOC2 审计需要 X"
- 记录决定的评论："我们决定采用方案 B，因为方案 A 需要改动 billing 服务"
- 标题类似计划的父 issue："Q3 企业就绪" 或 "降低支付失败率"
- 附加的 PRD 或规格说明
- 诸如 `customer:acme`、`incident-followup`、`compliance`、`perf-regression` 等标签

## 常见陷阱

- **范围漂移。** PR 引用的工单可能已被关闭后重新打开，且范围已变。请阅读完整历史。
- **机械式模板。** 一些团队要求填写"Why"部分，但内容全是样板文字。"提升用户体验"之类的泛泛文字大概率不是真正的答案。
- **过时工单。** 旧工单通常反映的是已经改变的计划版本。请检查日期，并与代码的发布日期交叉核对。
- **标记为重复后关闭的链条。** 沿着 duplicate-of 关系回溯到规范工单。
- **私有工作区内容。** 如果无法访问某个 issue，请将其记为信息缺口，而不要猜测。

## 需要返回的内容

对每个相关工单：
- 工单 ID 和标题
- 从描述或评论中引用的问题/动机（原文引用，不要改写。综合者需要精确原文来进行引注）
- 标签、父 issue、项目
- 作者、创建日期、关闭日期
- 如有的话，工单链接
