# 审查评分标准

根据相关的视角进行审查。并非每个视角都适用于每一项变更。

## 正确性

代码是否真的做到了意图中要求的事情？

- 边界情况：空输入、nil/undefined、边界值、并发访问
- 错误处理：错误是被捕获、向上传递，还是被静默吞掉？
- 差一错误、类型强制转换、整数溢出、字符串编码
- 状态管理：竞态条件、过期闭包、悬空引用
- 正常路径和异常路径是否都能工作？
- 幂等性：如果该操作运行两次，或者之前的运行在中途崩溃，会发生什么？如果答案是“取决于遗留的状态”，那么就缺少一个对账步骤。
- 并发：如果多个参与者可以访问同一个可变状态（文件、分支、共享数据），访问是否通过结构化方式串行化（锁、顺序阶段、独占所有权），还是依赖无法保证的约定？

当你发现潜在的 bug 时，追踪执行路径。不要只是标记“这里可能是 nil”。要展示导致其为 nil 的调用链。

## 根本原因与表面症状

代码是在修复真正的问题，还是在掩盖症状？

回答这个问题往往需要查看已修改文件之外的代码。阅读周围的代码（调用方、被调用方、类型定义、同级模块），并理解变更所处的架构。使用你可用的工具（Read、Grep、Glob）追踪调用链、阅读类型，并理解代码存在的原因，然后再判断该变更是否解决了正确层面的问题。

- 掩盖更深层不变量违反的保护子句
- 隐藏了已损坏契约的重试逻辑
- 掩盖建模错误的类型强制转换
- 一种变通方案：为什么需要它？正确的修复应该是什么样的？
- 在模块 A 中的修复，实际上应该是模块 B 契约中的修复
- 在结构更合适的地方使用说明：如果修复方式是一条注释写着“不要做 X”，或者是某个人必须记住的约定，要询问它能否改为类型约束、lint 规则或运行时检查，从而让错误的做法变得不可能发生

## 结构完整性

代码是否很好地融入了它所属的系统？

- 边界纪律：验证是否位于系统边界处，还是散落在业务逻辑中？在数据进入系统时验证一次，然后在内部信任它。
- 抽象层级：代码是否混合了高层编排与底层细节？
- 耦合：此变更是否引入了会使未来修改更困难的依赖？
- 数据模型契合度：数据结构是否与实际访问模式相匹配？
- 外挂式与整合式：如果在一开始就已知道新需求，代码会是现在这个样子吗，还是该变更感觉像是打补丁式地附加在现有设计上？
- 遗留的双路径：该变更是否引入了新 API，同时保留旧 API 继续存活？如果没有外部使用方，应在同一批次中迁移调用方并删除旧路径。不要留下会变成永久存在的兼容层。

不要因为简单代码缺少抽象而扣分。过早抽象比重复更糟。

## 验证

仅通过阅读代码，你能判断它是否正确工作吗？

- 是否有测试？测试的是行为还是实现细节？
- 是否有能够捕获回归的断言或不变量？
- 如果这是一个 bug 修复：是否有针对该 bug 的测试？
- 如果这涉及集成边界：完整路径是否经过测试？
- 检查真实对象，而不是代理。如果代码通过文件 mtime 或缓存状态而不是读取实际值来检查存活性，这就是一个验证缺口。
- 对于委派或异步工作：代码是验证实际的输出产物，还是信任自我报告和摘要？

## 复杂度预算

复杂度是否与代码所完成的工作相匹配？

- 在不损失正确性或清晰度的前提下，可以更简单的代码
- 只服务于一个调用点的抽象
- 为尚不存在的情况而设置的配置或参数化
- 死代码、未使用的导入、残留参数
- 过度设计：没有当前调用方的“以防万一”代码路径
- 为过渡期稳定性而保留、但已不再需要的过时兼容路径。如果迁移已完成，就删除脚手架
- 用户体验是否足以证明该复杂度的合理性？每个功能、控件和选项都应当证明其存在的价值。半成品功能比缺失的功能更糟。

除非更简单的方案是错误的，否则简单更好。

## 安全

对于每一项安全问题，都要追踪输入在代码中的路径并将其展示出来。

- 未经清理的用户输入流入危险的汇点（SQL、shell、eval、innerHTML）
- 新端点中的认证/授权缺口
- 代码、日志或错误信息中的密钥
- 安全关键路径中的 TOCTOU（检查时间与使用时间不一致）
