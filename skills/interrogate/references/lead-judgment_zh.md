# 主导者判断框架

## 过滤原则

### 挑剔性噪声

评审者，尤其是对抗性评审者，往往会把评审内容填满。如果他们没有找到严重问题，就会把 nit 级别的意见夸大来填充篇幅。如果评审者的发现全部是 nit 和风格偏好，说明代码大概率没有问题。请直接说明这一点。

### 假设性与实际性

“如果有人在这里传入 null 会怎样？”只有在调用方确实可能传入 null 时才算发现。请追踪调用点。如果输入已在上游校验，或类型系统阻止了这种情况，则驳回该发现。评审者基于 diff 工作，往往看不到完整的调用链，而你可以看到。

### 过早抽象警告

评审者常建议提取函数、添加接口或创建抽象。这段代码是否需要以第二种方式变更？如果不需要，这种抽象就是过早的。在当前范围内，简单的内联代码优于过度设计的整洁抽象。

### “我会用不同方式做”

这是代码评审中最常见的误报。仅表达“我更喜欢另一种方法”的发现，既不是缺陷，也不是设计缺陷，除非评审者能证明当前做法存在具体问题，否则不可执行。驳回这类发现，并说明原因。

### 上下文缺失信号

留意那些显示评审者并未理解上下文的发现：
- 建议修改作者既没有编写也没有修改的代码
- 标记与代码库其余部分一致的模式（评审者只是不了解这一点）
- 推荐与你所知约束相冲突的方法

这些是评审者在信息有限的情况下犯的善意错误。应礼貌地驳回。

## 评审者正确时

不要仅因为发现令人不舒服就驳回。对抗性评审的全部意义在于捕捉你可能遗漏的问题。以下情况表明某个发现值得关注：

- 多个模型独立标记了同一问题（共识信号）
- 该发现指出了具体的执行路径，而非假设情形
- 该发现揭示了你对代码心智模型中的缺口
- 你读到该发现时想“……确实如此”

对安全发现和正确性缺陷的驳回要格外谨慎，即使它们只来自单一模型。
