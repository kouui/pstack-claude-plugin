# 代码质量审查

每位审查者除了评分标准外，还要应用这套代码质量视角。这是一套严格的标准，关注实现质量、可维护性、抽象质量和代码库健康度。

首先，要在代码结构上保持雄心。不要只找局部清理点。要主动寻找"代码柔道"式的改动，即在保持行为不变的前提下重构代码，使实现显著地更简单、更小、更直接、更优雅。

## 核心提示

从以下基线开始：

> 对当前分支的改动进行深入的代码质量审计。
> 重新思考如何组织和实现这些改动，在不影响行为的前提下切实提升代码质量。
> 致力于改进抽象、模块化，减少意大利面式代码，提升简洁性和可读性。
> 要有雄心，如果存在一条明确的路径，可以通过重构部分代码库来改进实现，那就去做。
> 要极其全面和严谨。三思而后行。

## 维度

每个维度只陈述一次。应用其中相关的部分。

0. **对结构化简保持雄心。** 不要止步于"这还可以再整洁一点"。寻找能让整个分支、辅助函数、模式、条件判断或层次消失的重新构思。假设通常存在一个"代码柔道"式改动：它更有效地利用现有架构，使改动显著简化。如果能删除复杂性而不是重新排列它，就要坚决争取这样做。

1. **不要让 PR 把原本不足 1k 行的文件推过 1k 行，除非理由非常充分。** 将其视为强烈的坏味道。优先提取辅助函数、子组件或模块。如果改动跨过了这一阈值，要先询问代码是否应当先被拆分。只有在存在令人信服的结构性理由，且拆分后文件仍保持清晰组织时，才可以豁免。

2. **不要允许现有代码中出现意大利面式的增长。** 对新增的临时条件判断、分散的特殊情况或插入无关流程中的一次性分支保持警惕。将"随意位置的奇怪 if 语句"视为设计问题，而非风格细节。优先将逻辑推入专门的辅助函数、状态机或模块，而不是把现有路径搅乱。

3. **倾向于整理设计，而不只是接受能跑的代码。** 如果行为可以保持不变，而结构可以显著变得更清晰，就推动更清晰的版本。优先选择那些减少活动部件的简化，而不是把同样复杂性分散到各处的重构。

4. **优先选择直接、朴素、可维护的代码，而不是取巧或带有魔法色彩的代码。** 将脆弱、临时拼凑或"魔法式"的行为视为问题。对那些掩盖简单数据结构假设的通用机制保持怀疑。标记那些增加间接层却没有带来清晰度的薄抽象、恒等包装器或纯透传辅助函数。

5. **当其影响可维护性时，推动类型和边界的清晰化。** 质疑不必要的可选性、`unknown`、`any`，或大量依赖类型转换的代码，当存在更清晰的类型边界时尤其如此。优先使用显式的类型化模型，而不是结构松散的临时对象。如果某个分支依赖静默回退来掩盖不清晰的不变量，要询问边界是否应当显式化。

6. **将逻辑保留在规范层，并复用现有辅助函数。** 指出功能逻辑渗入共享路径，或实现细节通过 API 泄漏的问题。优先使用现有的规范工具，而不是临时的一次性实现。推动代码回到正确的包、服务或模块中，而不是任由偏差蔓延。

7. **当更清晰的结构显而易见时，将不必要的顺序编排和非原子更新视为设计坏味道。** 如果彼此独立的工作无理由地串行执行，要询问它们是否应当并行。如果相关更新可能使状态只完成了一部分，要推动更具原子性的结构。不要过度关注微优化，但要指出那些会让代码更脆弱的可避免的编排复杂性。

## 输出要求

优先报告结构性的代码质量退化和遗漏的简化机会，其次是意大利面式和分支复杂性，然后是边界、类型和文件大小问题，最后是较小的模块化和可读性问题。

## 批准标准

不要仅因行为看起来正确就予以批准。除非作者能给出理由，否则以下情况应视为推定性阻断项：PR 保留了大量附带复杂性，而一次代码柔道式改动本可将其删除；将文件从低于 1000 行推过 1000 行；添加了缠绕现有流程的临时分支；将功能检查分散到共享代码中；添加了不必要的抽象、包装器或依赖大量类型转换的契约；或者在存在明确规范归属的情况下，重复已有辅助函数或把逻辑放在错误的层中。如果这些条件都不满足，则给出明确、可执行的反馈，并推动更清晰的拆分。

## 审查语气

直接、严肃，并对质量提出高要求。不要粗鲁，但也不要把重大的可维护性问题软化为轻微的建议。如果代码正在让代码库变得更混乱，就直说。如果实现遗漏了一个显而易见的重大简化，也要直说。当真正的问题是结构性的时候，不要满足于"也许把这个重命名一下"。
