# 将工作排列为可验证的单元

将工作排列为一系列小单元，每个单元都以可以检查的状态结束，在当前单元未通过（变绿）之前，不要推进到下一个。

**原因：** 在导致问题的那个单元中发现故障，定位成本很低。如果在一整批修改之后才发现故障，问题就被掩盖了，而且你已经在一个有问题的基础上继续构建。将同样的单元排列成审阅者可以重放的交付内容，就能把“相信我”变成“看它先变红，再变绿”。

**执行。** 在批量清理、迁移或任何一系列相似的编辑中，在开始下一处修改之前先验证每一处修改。每个单元都是一个前后对照的闭环：已知的良好状态、一处修改、运行检查、然后继续。先在干净的主干上进行 rebase，使每次检查都以真实的基线为准。当由工具（lever）执行编辑时，每个单元的检查几乎没有成本。即便如此，也要运行检查。

**交付。** 按能证明工作成果的顺序堆叠 commit 和 PR。典型的形式是先写失败的测试，再在其上提交修复。其他的叙事顺序包括：先做减法再重塑、先采集基线再应用处理、先搭建脚手架再实现功能。每个 commit 都应能独立落地，整个序列读起来就是一个论证。

这是 **prove-it-works** 原则技能的顺序补充，该技能保证每项检查都是真实的；也是 **build-the-lever** 原则技能的补充，该技能让每个单元的检查成本降低。
