# 理由模板

随类型草图一同交付的散文。一页篇幅。标题采用句首大写的句式，不要套话。用实际内容替换斜体提示。

## 问题

*一段文字。我们要做什么，以及现有系统或约束中有哪些因素使得该形态并不显而易见。如果 [阶段 A](../SKILL.md#phase-a-ground-the-problem) 发现了设计必须遵守的约束（需要互操作的现有类型、不能破坏的调用方、跨越我们边界的不变量），请在此处点明，使读者看到与你相同的约束。*

## 用法（调用方视角）

*先写这一节，早于类型草图。展示消费者所阅读的 README 或快速入门，以及其自身代码中两到三个真实的调用点。包括导入什么、调用什么、返回什么。[结构](#shape) 中的类型草图由此推导而来。两者必须一致。若二者不一致，应将草图调整到与用法一致，而不是反过来。调用方的体验即规格，类型服务于它。*

## 结构

*推荐的架构。先数据结构，然后是数据如何流经各个签名。点明承重的决策。说明哪些不变量编码在类型中、校验位于何处，以及系统刻意不做什么。明确判断接口深度：说明公开接口隐藏了哪些复杂性、对调用方暴露了什么，以及为何该接口不大于所需。对每个决策引用其背后的原则（例如 `per boundary-discipline`）。不要复述原则本身。*

## 综合决策

*由 [arena](../../arena/SKILL.md) 填写。记录哪个候选成为基础方案及其原因，从其他各候选中吸收了什么，以及拒绝了什么及其原因。*

## 已接受的权衡

*所选形态做出的每项权衡对应一条要点。格式为："我们接受 X，以换取 Y。"凡是未来读者可能误认为是疏忽的内容都要写明，包括看起来像过早优化或过早简化的内容。*

## 已考虑的替代方案

*必填。至少列出一个具体的替代形态，并用一行说明其落选的原因。以接口深度而非仅以实现的简单程度来评判每个替代方案。说明它对调用方暴露了哪些复杂性，以及它隐藏了哪些复杂性。当设计空间中确有实质竞争者时，这里可以列出两到三个替代方案。当约束迫使得出唯一答案时，列出一个即可，结论表述为"这是唯一可行的形态，因为……"。避免罗列同一形态的各种变体。本节仅涵盖所选形态考虑并拒绝的设计替代方案，不包括其他运行器候选。*

## 未决问题与风险

*在草图过程中你注意到的、需要人类权衡的事项，以及在实现开始前值得标记的风险。请以问题的形式表述，而非断言，使人类的回答即为解决方案。*

## 下一步实现

*针对该草图第一件要构建的事情。一句话。即在综合（或在选择加入的检查点通过阶段 D 签核之后）立即开始编写的内容。*
