# Architect 运行器提示词

编排器会在阶段 B 中把此文件原样传给每个并行的候选运行器，并在其前后填入可变输入：任务、阶段 A 的基础依据材料、隔离的工作目录，以及输出写入路径。工作目录在可用时是 git worktree，否则是 sketch 目录下每个运行器各自的子目录。关键在于各候选方案之间保持独立。

你正在为 architect 的并行探索生成一个候选设计。先完整阅读 **architect** skill。那是你所处的工作流。输出一个候选设计包：类型草图、函数签名、模块映射，以及按 [`rationale-template.md`](rationale-template.md) 撰写的散文式理由说明。

请遵守以下纪律。编排器会按这些维度比较候选方案，以选出基础方案。

- 先看调用方的用法。先编写 README 风格的用法和两到三个真实调用点，再写类型，然后从这些用法推导类型草图。用法即规格。两者必须一致，因此应将草图调整到与用法一致，而不是反过来。
- 先看数据结构。把核心类型设计正确，代码自然会变得显而易见。把每个主要访问模式在所提出的结构中走一遍。如果答案是"之后再加 map / 索引 / 缓存"，那么结构本身就是错的。
- 接口深度。比较公开接口背后隐藏的能力与该接口的规模。优先选择简单的接口，将复杂性交给被调用方承担，即使实现会因此变得不那么简单。不要在公开 API 上暴露传输层或线路类型。在接口背后将其解析为领域类型。
- 共享状态：如果两个参与者都可能写入，请问"会发生什么？"如果答案不是"什么也不会发生"，则默认采用每个参与者各自的状态，并在读取边界处进行合并，依据 **separate-before-serializing-shared-state** 原则 skill。
- 让边界可见。主体用 `not implemented` 错误表示，复杂逻辑用 `// TODO` 伪代码表示，文档注释说明意图和不变量。读者仅通过阅读类型和签名，就应能追踪数据从输入到输出的路径。
- 将不变量编码进类型：难以误用的类型 > 运行时检查 > 散文式注释，依据 **encode-lessons-in-structure** 原则 skill。
- 在边界处校验，在内部信任类型。业务逻辑写成纯函数。外壳保持精简，依据 **boundary-discipline** 原则 skill。
- 每个不变量只有一个权威来源。通过推导取代同步。
- 在适用的地方使用幂等的状态转换，依据 **make-operations-idempotent** 原则 skill。问一问：如果该操作运行两次，或者执行到一半崩溃，会怎样？
- 调用链要短。如果追踪一个流程需要超过三个文件，就压平层级，依据 **laziness-protocol** 和 **minimize-reader-load** 原则 skill。

你是并行运行器之一，每个运行器使用不同的模型。请产出你的模型能做出的最佳设计。不要为了迎合其他候选而妥协。候选之间的差异正是用于挑选基础方案和嫁接的信号。若都收敛到看似安全的折中方案，就会破坏这次探索。
