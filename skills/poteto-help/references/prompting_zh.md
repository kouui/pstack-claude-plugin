# 撰写提示词

提示词应说明意图以及完成的检查标准。playbook 会提供步骤，因此几句平实的话胜过一份详细的规格说明。

## 应包含

- 目标。说明哪里有问题，或用户想要什么。
- 完成检查。它可以通过，也可以失败。"做得更好"和某个时长都不是检查标准。
- 需要展示的证明。要求提供真实的命令输出、流程的视频、存储的值，或前后对比的数字。
- 用户已知的信息。一个症状、一个复现步骤、一段日志或一个链接，可以省去代理的搜索工作。
- 真实的约束。"先复现"、"暂时不要改任何代码"、"行为零变化"以及"继续之前让我先审阅"，每一条都会改变代理的行为。

## 应省略

- 具体做法。说明要达成什么，并给代理留出寻找更好方法的余地。
- 技能或步骤的清单。手写的顺序会丢掉或打乱 playbook 保留的步骤。只有在需要覆盖某个选择时才点名技能。
- 用户自己对原因的推测，直到代理用自己的话复述了问题为止。预先给出的猜测会缩小搜索范围。

## 先加载上下文

- 对于内容杂乱的报告，要求代理在做任何其他事情之前，先用自己的话、以平实的英文复述潜在问题。误解会在任何代码出现之前就暴露出来。
- 在新的对话中，先用 `/recall` 回顾关于该主题的早期工作。旧对话中保存着新代理所缺少的上下文。
- 在修改不熟悉的代码之前，用 `/how` 了解其机制，用 `/why` 了解其原因。没有经过追踪建模的代理，会在第一个看似合理的位置修复症状。
- 用 `/teach` 为某个选择陈述理由，例如"说服我它修复的是原因而不是症状"。一个论证比一份摘要更容易检验。

## 在计划之前先设计

- 永远不要直接采用第一个设计。要求为几个备选方案制作原型，UI 方面附上截图或视频，然后基于证据做出选择。
- 让原型回答悬而未决的问题。不要以对抗性的方式审阅抽象的计划，因为审阅者会虚构出从未发生的风险。
- 对于共享包或 API，先要求提供 README 或教程，再倒推回代码。文档会成为代理自我核对的目标。
- 只有在设计确定之后，才要求提供计划。计划中的每个步骤都要以一项检查结束。

## 简短的后续跟进

- 一旦对话中已包含任务，"do it"、"continue" 和 "keep going until done" 就是完整的提示词。
- 当主题改变时，以 "new task" 开头。否则该模式会把这条消息当作下一步。

## 离开之前

- 说 "im going to bed" 或 "im stepping away"，以便代理停止提问。
- 将完成条件写成每次迭代都能运行的检查，并把该判定条件交给 `/loop`。
- 要求基于指定的基线分支新建一个 worktree。
- 预先回答代理可能会停下来询问的事项，例如 "don't ask me before committing"。
- 要求保留一份决策日志，以便事后审计。
- 给出退出条件："如果你真的卡住了几个小时，就停下来，写明原因。"

## 用一句话进行纠偏

- 重申目标："i said the goal is to repro. i did not ask for a fix yet."
- 点名原则："apply prove it works. show me the real output, not the build log."
- 原则名称之所以有效，是因为代理已经读过该规则。它的回复会说明该规则改变了哪个决策。
