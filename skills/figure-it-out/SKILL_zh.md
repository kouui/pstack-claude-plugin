# Figure it out

在 Claude Code 中，遵循本 skill 之前，每个会话先阅读一次[Claude Code 适配器](../../docs/harness/claude-code.md)。它把 pstack skills 中的 Cursor 名称映射到 Claude Code。

当任务不匹配任何 playbook 时，就设计一个。在编写任何代码之前，交付物是工作流本身：一系列阶段，它们根据任务调整严谨程度，运行科学方法，并留下一条人类可以在离开后审计的决策记录。

## 开始

打开一个待办列表，第一项是阅读 **poteto-mode** skill 中的 Principles 部分。然后把下面的各阶段添加为待办项。

## 阶段 A：界定

先摸清情况，再做决定。在能够陈述以下内容之前，不要开始运行：

- 完成的定义，写成可证伪的判定条件（**prove-it-works** 原则 skill）。
- 范围，量化：粗略的单元数和工作量，以及摸底时发现的阻碍因素。
- 严谨程度，倾向于偏高。单向门和高影响范围的决策需要更多严谨性。可逆的低风险步骤需要较少。严谨性体现在关卡和产物上，而不是"再努力一点"。

在投入长时间运行之前，先展示框架和权衡取舍。可逆的工作直接推进（**never-block-on-the-human** 原则 skill），但持续数小时的运行应设置一个检查点。

## 阶段 B：设计工作流

将工作分解为原子的、可独立落地的单元。按照风险最高的未知项优先排序。脚手架和验证先于功能开发（**foundational-thinking** 原则 skill）。

- 在工作开始前构建验证工具，并从变更前的状态捕获基线，使检查可以读作"旧值与新值"的对比。
- 对于单向门的设计决策，运行 **architect** skill（它会运行 **arena**）。对于形态已经具体的机械性工作则跳过。对已定型设计再做一次 arena 属于过度设计（**laziness-protocol** 原则 skill）。
- 决定哪些内容需要扇出。只在各个接缝之间并行，并且为每个 worker 分配独立的 worktree 或分支（**separate-before-serializing-shared-state** 原则 skill）。不要过度扇出。根据 **poteto-mode** skill 中 Subagents 部分的说明，为每个 subagent 选择适合该工作的推理级别以及快速或标准速度。
- 把设计好的阶段列表写下来。这份列表就是人类要审阅的内容。

然后执行设计。把其中的步骤作为具体条目添加到待办列表中，位于阶段 C 与阶段 D 条目之间。每一步都在阶段 C 的循环纪律下运行，并且随着每一步落地穿插记录阶段 D 的日志，每完成一步记一行，而不是把整个记录留到最后。

## 阶段 C：运行循环

每个单元都是一次实验。陈述假设，做最小的改动，在真实产物上依据判定条件进行度量，若有所推进则保留，若没有则回滚。应用 **sequence-verifiable-units** 原则 skill，在开始下一个单元之前先验证当前单元，而不是把检查集中到最后。

- 通过检查产物来验证，绝不依赖自我报告。当某件事通过得过于轻松时，先怀疑观察方法，再怀疑系统本身。
- 将委派的工作与评判者配对。如果 worker 钻了关卡的空子，就重置并加固契约。如果关卡本身有误，则在它自己的变更中修复关卡，而不是绕过它。
- 结论只有 VERIFIED、NOT VERIFIED 或 INCONCLUSIVE 三种。Inconclusive 不等于通过。不要隐藏负面结果。

## 阶段 D：保留审计记录

通过 **show-me-your-work** skill 记录运行过程。figure-it-out 的工作通常足够雄心勃勃，因此值得把记录一并提交，使审阅者可以在 PR 中阅读它。记录加上 diff，才能让人类回来后信任这项工作。

## 阶段 E：验证并交还

依据阶段 A 的判定条件，在真实产品上检查整体，而不仅仅是检查工具。把任何反复出现的修正编码为关卡、lint 规则、检查或脚本（**encode-lessons-in-structure** 原则 skill）。

**回复：** 你设计的 playbook、严谨程度及其理由、决策记录的路径、依据判定条件已验证的内容，以及仍未解决的问题。
