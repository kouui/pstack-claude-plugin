# Recall

在 Claude Code 中，每个会话开始时先阅读一次 [Claude Code 适配文件](../../docs/harness/claude-code.md)，然后再按照本技能操作。该文件把 pstack 技能中的 Cursor 名称映射到 Claude Code。

**在开始或恢复工作之前，你要重建用户最近的工作上下文，并交回一份简洁的摘要，说明事情现在处于什么状态以及下一步该做什么。**

保持简洁，聚焦主题。只阅读相关线程所需的内容，然后停止。

你的上下文存在于两份记录中。你自己的聊天历史记录了你做过和决定过的事。共享记录包含与同一段代码相关、但使用了其他名称的所有事件：用户持续反馈的症状、已发布后又被回滚的修复、生产环境中仍在触发的错误。**why** 技能会在这第二份记录中搜索，范围包括源代码管理、问题跟踪器、聊天和 issue 频道、长篇文档以及错误跟踪系统。一个存在大量遗留缺陷的功能，其大部分来龙去脉都保存在这里，因此不要仅根据你的对话记录来重建它。

对话记录位于 `~/.cursor/projects/<slug>/agent-transcripts/<uuid>/<uuid>.jsonl`，其中 `<slug>` 是去掉开头斜杠后的工作区路径，并把每个 "/" 替换为 "-"（因此 `/Users/you/proj` 会变成 `Users-you-proj`）。每一行是一条聊天消息。

1. 先分类，再路由。要恢复某一次特定的历史聊天，应使用 `session-pickup` 操作手册，而不是本技能。把习惯转化为可长期使用的技能属于 `automate-me`。给你的工作写一份易读的人类摘要是另一项任务。Recall 是在你行动之前加载最近多次聊天中的工作上下文。如果用户已经给出了完整的状态摘要（路径、分支、变更内容），就直接使用它，跳过挖掘步骤。
2. 先锁定范围，再开始搜索。确定时间窗口（"recent" 是一个真实的范围，默认为最近 7 天）、命名的主题（如有），以及工作区（默认为当前活动的工作区。未经要求，绝不读取其他项目的对话记录）。把范围明确说出来。绝不悄悄地把 "all" 改成 "recent N"。
3. 在你的聊天历史中分片扇出。启动并行的子代理，使用快速、低成本的模型，每个子代理负责语料的一个切片。告诉每个子代理按真实修改时间排序候选项（`ls -t`），绝不按 UUID 名称排序；先对主题进行 grep，然后只读取匹配的聊天，并且只读取其中相关的部分；跳过当前聊天以及明显的噪声（子代理、评测和测试聊天）。每个子代理返回相同的结构，每个聊天一个块：主题、用户的目标、决定、未结线程、遇到的困难和纠正，以及产出物（PR、工单、分支），每项都要引用聊天 UUID。如果只有一两个聊天，则跳过扇出，直接搜索。原始对话记录留在子代理中，主线程只接收它们的发现。根据 **poteto-mode** 技能中子代理部分的规定，为每个子代理选择合适的推理级别以及快速或标准速度。
4. 只要主题涉及某个功能、文件、子系统、领域或 bug，就要搜索共享记录。这是默认要求，而不是可酌情判断的事项，"my work on X" 也不构成豁免。把这项工作交给 **why** 技能的各个源调查员，但要把它们的问题从"为什么这样构建"改为"当前状态是什么、哪些尝试过且没有成功、用户仍在反馈什么"。复用其各来源的操作手册，与聊天历史挖掘并行运行调查员，并继承其准则：每个来源一个调查员，空结果本身也是发现，不可用的 MCP 要跳过并说明。把返回的内容整合进简报。只有在完全没有指定目标的纯活动回顾中（"我这周做了什么"），才可以跳过这一步，此时你自己的历史和实时状态就是全部答案。
5. 对照实时状态进行验证。对挖掘和搜索得到的 PR、分支和工单，用 `git` 和 `gh` 逐一核对。当答案取决于某个代理实际做了什么（它运行的工具、读取的文件、遇到的错误）时，要阅读完整对话记录，而不只是本地裁剪后的副本。
6. 按照下面的输出约定撰写简报。按线程分组。聚焦于指定的主题。

## 输出约定

先给出摘要，然后是线程状态，再是问题，最后是下一步行动。更详细的内容放在后面，或者被删减。

- **摘要。** 最多 5 个要点。这项工作是什么，以及整体上处于什么状态。
- **线程。** 每个线程一行，前缀恰好为一个状态标签：`[merged #N]`、`[open PR #N]`、`[in flight <branch>]`、`[verified, uncommitted]`、`[reverted #N]` 或 `[planned, not started]`。没有标签的线程视为尚未完成，因此必须加上标签。
- **问题。** 最多 5 个，只列反复出现的问题。包括用户持续反馈的症状，以及已发布后又被回滚的修复，使下一次尝试能从上一次失败的地方开始。
- **下一步。** 最有价值的单个下一步行动，要具体。

与本功能无关的相邻功能或工单不要列出，除非它阻塞了本功能。当摘要和线程行超出一屏时，先删减细节，再删减线程。简报要通过 **unslop** 技能撰写；聊天中的发现要通过 UUID 引用，共享记录中的发现要通过其来源引用（PR 编号、工单 ID、聊天永久链接、错误跟踪系统中的 issue）；在任何公开输出之前，先清除私人上下文。

**回复：** 按照上述约定给出简报。
