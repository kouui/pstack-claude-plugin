# 测试行为,而非实现

测试是关于代码对其用户所做之事的断言:调用方、终端用户或其他服务。行为是这些用户通过他们所使用的接口能够观察到的内容。这包括返回值、错误、他们可以读回的状态,以及对代码之外系统的影响,例如发出的请求、写入的数据行或发出的消息。实现则是用户无法观察到的内容:私有辅助函数、内部调用顺序、中间数据,以及是哪个内部协作者完成了工作。

请通过两种假想的修改来评判每个测试:

- **破坏行为。** 让代码返回错误的值、跳过某个效果,或者重复执行某个效果。如果测试仍然通过,说明它什么也没证明。通常的原因包括:断言比契约宽松、期望值由被测代码计算得出、复述的常量或提示字符串从未运行读取它的代码,以及对测试自身构造的数据进行断言。
- **改变内部实现。** 保持所有可观察的结果不变,重构其底层代码。如果测试因此失败,说明它被绑定到了实现上。每次重构都需要重写,而且仍然无法捕获任何 bug。

保留能够捕获第一种修改、并能经受第二种修改的测试。重写或删除其余的测试。要编写同时满足两者的测试,应通过用户的接口、使用具体输入来驱动代码。期望值应从需求推导,而不是从运行代码的结果得出。断言契约所承诺的内容,不多也不少。

决定因素是契约,而不是断言的形式。当"空购物车永不扣款"是承诺时,断言支付客户端未被调用就是行为。应同时配以一个会发生扣款的用例,以证明测试能够观察到调用。被模拟的外部服务所接收到的负载属于行为,因为该服务能够观察到它。对内部辅助函数的调用属于实现,因为没有用户能够看到它。空列表是"没有记录匹配"时的精确答案,而当测试只需要"某个结果"时,它就是一种空洞的检查。精确的错误消息所约束的是没有调用方会读取的措辞。调用方据以分支判断的错误类型才是契约。

测试可以约束一个不变量,而不是某次调用,例如某个键必须同时存在于两张表中,或者编译期类型检查。不变量本身就是行为。
