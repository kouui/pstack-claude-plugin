# Ketchup

用平实的语言向用户汇报自其在 `/ketchup` 之前写下的最后一条消息以来，本聊天中发生的变化，并帮助他理解每项变化，而不只是告诉他目前处于什么状态。然后列出所有等待其决定的事项，使他仅凭你的回复即可做出决定。通知和子 agent 的结果不算作用户的消息。假设用户只记得自己的最后一条消息，而不记得之后的任何内容。

使用 [`/bro`](../bro/SKILL.md) 的语气，而非其任务：用平实的词语，简短的句子，不用行话，像一个人向另一个人汇报情况那样。说明变化对用户意味着什么，而不是你是如何完成的。说"测试通过"，而不是"CI 是绿色的"。除非用户需要其中某项来采取行动，否则省略哈希值、文件路径、命令、构建编号和测试数量。用用户能够理解的名称称呼每个 PR、分支或 agent，而不是你自己编造的标签。如果某个事实需要上下文才能理解，就提供上下文，否则省略该事实。

## 收集变化

本轮保持只读。只使用你已经掌握的信息制作图示：不要修改代码，不要启动应用或任务，也不要发布任何内容。收集你自该消息以来完成的工作、子 agent 的报告，以及本聊天中其他人的消息。检查本聊天涉及的每个 PR、CI 运行或 agent 的当前状态。将你要展示的每个数字与其来源的事实进行核对，并在有更正时予以说明。

行动事项是只有用户才能执行的决定或步骤，例如产品选择、审批、不可逆的操作，或你缺少的访问权限。包括仍在等待用户的事项，即使它是在其上一条消息之前提出的。你自己仍能完成的工作不是行动事项。绝不为了填充回复而编造决定。用户没有要求且工作也不需要的步骤不是行动事项，除非它是不可逆且正在等待用户的：此时给它一行，不配图示。

一个决定可以涵盖多个条目，例如等待合并的一组 PR 中的每一个。对于每个条目，收集其链接、它对用户的影响、你选择该方案所依据的证据、其风险，以及你的选择。对于决定所需但你不知道的事实，写"未知"。你没有的链接就不要列出。

## 撰写回复

把文字用在决定上，而不是用在叙述上。发生的事情控制在 100 字以内（不计图片），发生的事情越少，篇幅越短。省略对用户没有影响的工作。每个条目约 30 字。回复会随条目数量增长：两个条目总共需要远少于 150 字（不计图片），三十个条目则需要多得多。绝不为了符合字数限制而删减条目或缩短条目：不能用数量代替列表，也不能用链接代替条目。链接可以提供更多深度，但仅凭回复本身就必须足以做出决定。

用一句简短的话开头，说明什么在等待用户，或说明没有任何事项在等待。行动事项会给出具体细节。如果什么都没有发生，也没有任何事项在等待用户，就直接说明并结束。

然后先展示发生了什么，图片优先。内嵌工作产生的截图和视频，然后是解释某项变化的任何图表。接着为用户要求的每件事用一个简短的要点进行总结：说明其结果，以及它是已完成、仍在运行、已失败，还是尚未检查。每一行都要像你大声说出来那样书写："搜索变慢是因为缺少索引"，而不是"搜索审查：已完成"或"搜索变慢：缺少索引"。点名在过程中发现并修复的任何缺陷。每一行单独阅读时都必须保持正确。绝不将仍在等待用户的事项标记为已完成，并省略行动事项中已经说明的内容。在摘要下方，最多给出三行简短的文字，用来改变用户所了解的情况或其必须做的事。然后用一行说明你自己可以完成的剩余工作。

接着列出行动事项。提出由用户负责的决定，例如合并、批准或选择，并给出你的选择。你会首先采取的步骤写在你的选择中。任何必须先发生的事项，以及任何无法撤销的事项，也都写在你的选择中。即使是在多个选项之间做出的决定，也要给出每个相关 PR、issue 或 agent 的编号或链接。

让形式与决定相匹配。关于单个条目的决定写成一个要点：决定本身、你的选择、它对用户的影响、你选择所依据的证据，以及风险，并且条目名称只点明一次。当多个条目共享一个决定时，先写一次决定和你的选择，然后为每个条目单独写一个要点，按风险从高到低排列：其链接和名称、它对用户的影响、你选择所依据的证据，以及它的风险。只有当某个条目的选择与决定的整体选择不同时，才单独说明该条目的选择。即使风险很低，也要写出每个条目的风险，例如"低风险：只改变颜色。"只有当等待的代价不仅仅是延迟时，才说明其代价，例如存在截止日期或数据会丢失。

对于在多个选项之间做出的决定，列出每个选项所权衡的工作，并分别说明它给用户带来什么、需要付出什么代价，以及存在时的当前状态。这些代价就是该决定的风险，因此不要另外添加风险行。当上方的截图展示了这些选项时，就在每张截图下方写出每个选项的收益和代价。

## 图示

图示是一幅图片：截图、视频、Mermaid 图、来自 `/visualize` 的图表或图解，或生成的图片。即使带有前后对比列，Markdown 表格也不是图示。

当某件事通过图片比通过句子更容易理解时，就把它画出来：设计或系统如何运作，带有每个 PR 状态的 PR 堆叠或依赖链，修复前后的对比，或并排的选项。绝不画状态列表、行动事项列表，或没有任何连接的方框。绝不在文字或多个图示中重复同一事实。

让每个图示小到一眼即可读完：最多六个方框，每个方框最多八个词。标签要使用人们会说的平实词语，而不是"测试：通过"这类标签。需要一句话才能说明的事实，要么放在文字中，要么就不放。

当变化可见时，内嵌截图和视频，而不只给出链接。如果一项可见的变化没有截图，就在其摘要行标注"尚无截图"，并在那里说明屏幕上发生了什么变化。只根据你已掌握的事实绘制图表：用 Mermaid 图展示事物之间如何连接，用 `/visualize` 图表展示数字。绝不编造数字，也绝不绘制或生成你未曾捕获的屏幕画面。只链接确实存在的产物。
